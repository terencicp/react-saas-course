# Chapter 100 — Project plan: ship to production, then live-migrate the schema

## Substrate decision (architect's call — read first)

The chapter outline frames this project on a real Postgres + Drizzle + Vercel + Neon stack and lifts "the chapter-062 invoices surface." **Two facts force a re-frame the coder pipeline must honor.**

1. **Ch062's `solution/` has no database.** It backs invoices with an in-memory module store + cookie session (the architect's call there, for a zero-bring-up visible surface). But Chapter 100's *entire* teachable payload is a **real Postgres schema migration** (`invoices.total numeric NOT NULL` → separate `subtotal` + `tax`): `ALTER TABLE`, `information_schema.columns` probes, `coalesce` dual-read, `SET NOT NULL`, the `__drizzle_migrations` ledger. None of that is teachable against an in-memory store. So this project does **not** fork ch062's substrate — like ch065 did, it forks the **real-Postgres org/RBAC/audit backend lineage** (Postgres 18 + Drizzle 0.45 + Better Auth organization plugin + `tenantDb`/`withTenant` + `authedAction` + `audit_logs`/`logAudit`) and ports the ch062 invoices surface onto it. The render pipeline boots Docker Postgres + `pnpm db:migrate` + `pnpm db:seed` (the ch065 posture).

2. **The deployment half is by-hand, not codeable.** Vercel/Neon/GitHub/CI/rollback are real-world gestures the student performs in lessons 2 and 6 against live accounts; `project-inspector` boots `solution/` *locally in a browser* and cannot exercise them. So the **coder slices are exactly the three migration PRs** (expand/migrate/contract) run against local Docker Postgres — each a real, locally-runnable, render-checkable artifact. The deploy/rollback lessons produce **runbook docs** (`docs/runbooks/*.md`) the student writes by hand; the scaffold ships the `/api/health` route, the env validator, the CI workflow, the deployment-aware inspector panels, and `docker-compose.yml` so every deployment concept has a concrete on-disk home, and the lesson test files assert the runbook docs' load-bearing structure. Real Vercel/Neon/GitHub are **not** in the render pipeline (the ch065 posture for live third parties).

This diverges deliberately from the chapter outline's "fork ch062 / Vercel-Neon live" framing (a preliminary brainstorm). Every concept the unit teaches — expand-migrate-contract, dual-write/dual-read/backfill, `SET NOT NULL` promotion, the schema-state/split-coverage/dual-write/data-integrity inspector panels, the deployment-environment + build-source indicators, `/api/health`, the rollback caveat — is preserved and either locally-checkable (the migration cadence) or captured as a doc artifact (the deployment gestures). Coder agents build against local Postgres; nothing in `solution/` calls Vercel or Neon at runtime.

## Project goals

The project cements Unit 20 as one runnable discipline: the student takes a live, org-scoped invoices app whose `invoices` table carries a single combined `total numeric(12,2) NOT NULL` — a real anti-pattern — and evolves it into separate `subtotal` + `tax` columns through the **expand-migrate-contract** cadence, three reviewed migrations run against a real Postgres, with the running app and the live schema never incompatible. Coding cements five durable senior skills, each a "make the unsafe change impossible" lever: (1) **expand is additive-only** — two *nullable* `numeric(12,2)` columns matching `total`'s precision exactly, no app-code touch, no row rewrite, so the old fleet keeps working; (2) **dual-write is structural** — every mutation writes `subtotal`, `tax`, *and* `total = subtotal + tax` in one Drizzle `.set({...})` call, so a divergent row is unwriteable, with a transitional legacy-amount fallback so an in-flight post can't 422 mid-deploy; (3) **dual-read fall-through** lives once in the query helper — `coalesce(subtotal, total)` / `coalesce(tax, 0)` — so un-backfilled rows read correctly while `total` stays available; (4) **the backfill is bounded + idempotent** — batched `WHERE subtotal IS NULL`, loop-until-zero, run on `dbUnpooled`, safe to re-run, and ordered *after* the dual-write is live so no row slips through the gap; (5) **contract is the one irreversible move, kept smallest** — a single `DROP COLUMN total` plus the cleanup the bridge made trivial, with the type checker as the first net and one scoped grep as the second. The student practices each by filling stubs against a brief, running migrations against local Postgres, and reading the inspector's schema-state probe, split-coverage, dual-write, and data-integrity panels flip green as the cadence proceeds. Alongside, the student walks the deploy and rollback gestures by hand and writes the durable runbooks — the launch checklist, the migration log, and the rollback runbook with its bolded "an alias re-point does not undo a forward-only migration" caveat.

The goal is not a realistic app; it is to walk the canonical 2026 "live-migrate without an outage" workflow so the additive-expand / structural-dual-write / idempotent-backfill / smallest-contract reflexes are cemented. Features stay minimal: one money-column split, the carried-in invoices CRUD, no new app features.

In scope:
- `src/lib/invoices/actions.ts` — `createInvoice` and `updateInvoice`:

## Locked decisions

- **No live Vercel/Neon/GitHub at runtime; the migration cadence is the only coded student work.** `solution/` imports no Vercel/Neon SDK and makes no deploy-platform call at runtime. The inspector reads `process.env.VERCEL_ENV`/`VERCEL_GIT_COMMIT_SHA`/`VERCEL_URL` only and falls back to a `local`/`development` render when they are absent. The deploy (L2) and rollback (L6) are by-hand gestures producing runbook docs; coder slices are exactly the three migration PRs (S1/S2/S3) run against local Docker Postgres.
- **The cadence is forward-only and ordered: expand → migrate → contract, with promotion after backfill.** Expand adds **nullable** columns (no app touch, no row rewrite). Migrate writes all three columns structurally, reads via `coalesce`, backfills (idempotent, after dual-write is live), then promotes to `NOT NULL`. Contract drops `total` last (the only irreversible move). Never reorder; never add a `DROP`/`NOT NULL`/`RENAME` to the expand migration; never run the backfill before the dual-write.
- **Dual-write is structural — one `.set({ subtotal, tax, total })`.** Every money mutation writes all three columns in a single Drizzle `.set(...)` call with `total = subtotal + tax` (string-money: convert→add→format via the carried-in helper; `numeric` is `string` at runtime). A wrapper that "writes `total` separately later" is the divergence bug the data-integrity diff exists to catch — forbidden. The legacy-amount fallback (`subtotal = amount, tax = 0`) is at the action layer, transitional, removed in S3.
- **Dual-read fall-through lives once in the query helper** — a typed `sql` fragment `sql<string>\`coalesce(${invoices.subtotal}, ${invoices.total})\`` / `sql<string>\`coalesce(${invoices.tax}, '0')\`` in `listInvoices`/`getInvoiceDetail` (Drizzle 0.45 ships no `coalesce` helper — it is the `sql\`coalesce(…)\`` template, never an imported function), never scattered across call sites; removed in S3 (returns the pair directly).
- **The backfill is bounded, idempotent, `dbUnpooled`, by-hand.** Batched `WHERE subtotal IS NULL` (subquery `LIMIT`/`IN`), loop-until-zero, safe to re-run (a second run writes zero rows), run on `dbUnpooled` via `pnpm db:backfill`, never imported by the app, never inside a request. Trigger.dev for a real 200K-row backfill is named-not-built (the chapter outline's escape hatch).
- **`subtotal`/`tax` match `total`'s `numeric(12,2)` exactly.** Mismatched precision is silent money corruption — copy the producer's type. Both are `numeric` → `string` at the Drizzle runtime (matching the carried-in `total: string`); arithmetic converts at the app layer.
- **Migrations: `generate --name <verb>_<noun>` → review → `migrate`, never `push`.** Flat layout, the `__drizzle_migrations` ledger, statement-breakpoints between sibling `ALTER` statements in the expand + promotion migrations (metadata-only adds don't strictly need it, but the cadence keeps the shape consistent). The contract `DROP COLUMN` is one statement, no breakpoint. The student commits each reviewed `.sql`.
- **The carried-in mutation invariants hold unchanged.** Every money mutation keeps the `version` precondition + honest 409 conflict (`conflict(userMessage, current)`), the tenancy filter via `tenantDb`/`withTenant`, and the `logAudit(tx, event)` write in the same transaction (a money-shape migration must not lose audit coverage). The lifecycle actions (archive/restore/soft-delete) are untouched by the cadence.
- **`authedAction` + `tenantDb`/`withTenant` + `logAudit` are the only privileged/scoped/audited paths** (ch059 lineage): `createInvoice`/`updateInvoice` are `authedAction('member', schema, fn)`; the mutation + its audit row co-transact in one `withTenant`; reads go through `tenantDb(orgId)` / `scopedInvoices`. Refusals return a `Result`, never throw. No bare `db.<table>` in app code (the unscoped `db`/`dbUnpooled` is reserved for `scripts/` and the backfill).
- **`Result` is the carried-in 7-code union, unchanged.** No new codes. The 409 conflict is `'conflict'` carrying `current`; a forbidden role is `'forbidden'`.
- **The inspector is provided in full, renders at every cadence stage, never throws — and its probes use raw `sql`, never the typed query builder.** Its panels read whatever the schema currently is (schema-state via `information_schema.columns`, split-coverage counts, recent-10 dual-write rows, the `subtotal + tax <> total` data-integrity diff, the audit tail) — the pre-expand → post-contract progression is the teaching surface. **Load-bearing:** every probe is a `db.execute(sql\`…\`)` raw query (column names as SQL literals), **never** a typed call referencing `invoices.subtotal`/`invoices.tax`/`invoices.total` — so the *same provided `_data.ts`* compiles against both the `start/` baseline schema (`total` exists, `subtotal`/`tax` do not) and the contracted `solution/` schema (`total` gone), and a build never breaks because a column the typed builder expects is absent. The probes guard a missing column at runtime by checking the schema-state result first (rendering "n/a" for the `total`-dependent diff once contracted). Dev-only actions (`reset`/`switch`/`triggerTestError`) gate `NODE_ENV !== 'production'`. In production the page is admin-gated; locally it is open.
- **`/api/health` is unauthenticated, cheap, opaque.** No `runtime`/`dynamic` segment config (both are rejected under cacheComponents); `await connection()` first (Node is the default runtime), then a single `select 1` via `dbUnpooled`, `200 { ok: true, db: 'up' }` or `503 { ok: false, db: 'down' }` — never a connection string or error detail in the body (the launch-checklist endpoint).
- **The env validator is real and committed; `SKIP_ENV_VALIDATION` lives only in CI's typecheck/lint/test jobs.** `RESEND_API_KEY` is validated-not-used (the chapter outline's deliberate choice); `SENTRY_DSN`/`APP_URL` are values, not packages. Production must boot with the validator on (the L2 build-log demonstration).
- **The runbooks are doc artifacts, not code.** `docs/runbooks/{launch-checklist,migration-subtotal-tax,rollback}.md` ship as committed skeletons; the student fills them by hand (L2/L3/L4/L5/L6). `rollback.md` must carry the **bolded** "an alias re-point does NOT undo a forward-only migration" caveat + the four-step gesture + the `git revert` follow-up + re-enabling auto-assignment. The lesson test files assert these structures.
