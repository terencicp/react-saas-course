Every year, WebAIM scans the home pages of the top million websites and counts the accessibility errors a machine can detect. The 2026 run found a result worth pausing on: pages that used ARIA averaged roughly **59** detected errors, while pages that used none averaged about **42**. More ARIA, more errors, and the gap points the same direction in every report.

That doesn't make ARIA harmful. The pages reaching for it are attempting harder interfaces, and ARIA is the tool for those. But the same tool can cut the wrong way. ARIA is the first thing in this chapter that can make an interface measurably *worse* while the diff looks like an accessibility win. Semantic HTML and the shadcn primitives only ever help; ARIA is the one surface where you can ship a regression and feel good about it.

So this lesson is mostly about restraint. By the end you will know the **four** ARIA surfaces a web app engineer actually reaches for, roles, labels, descriptions, and live regions, and when *not* to reach for any of them. You will label an icon-only button so a screen reader can read it, announce a "Saved" toast and a search-result count to someone who can't see them, and wire help text to an input.

Frame this against the previous two lessons. Semantic HTML is the first move, and the shadcn primitives ship correct ARIA for the widgets they cover; together they handle about ninety percent of accessibility before you type an `aria-` anything. This lesson is the other ten percent: the custom widgets and the live state the primitive doesn't know about. Most of your ARIA will be a handful of attributes, and the skill is knowing which handful and stopping there.

## Use native HTML first: ARIA never changes behavior

One rule prevents most ARIA bugs before they exist. It comes straight from the <Term definition={"The WAI-ARIA Authoring Practices Guide — the W3C's official guidance on how to use ARIA correctly, including patterns for common widgets.\nWhen this course says 'the spec says', this is usually the source."}>WAI-ARIA Authoring Practices Guide</Term> (the APG), the W3C document that defines how ARIA is meant to be used:

> If you can use a native HTML element with the semantics and behavior you need, use it.

The same guide leads with the maxim this lesson is named after: **no ARIA is better than bad ARIA.** A control with no ARIA is a known quantity; a control with *wrong* ARIA tells the user something false, and a false signal is worse than silence.

One mental model explains why ARIA goes wrong so reliably:

**ARIA only changes what assistive technology announces. It never changes behavior.**

ARIA edits the *description* that <Term definition={"Assistive technology — the software and hardware people use to operate a computer non-visually or non-manually.\nScreen readers (VoiceOver, NVDA, JAWS), switch devices, screen magnifiers.\nUsually abbreviated AT."}>assistive technology</Term> (AT: screen readers, switch devices, magnifiers) reads aloud. It never touches keyboard handling, focus, or clicks, what the element actually *does*.

Here is the resulting mistake. You need a Save control, and you build it on a `<div>`:

<CodeVariants>
  <CodeVariant label="div + role (broken)">
    <div data-mark-color="red">

    ```tsx "role=\"button\""
    <div role="button" onClick={save}>Save</div>
    ```

    </div>
    This renders, it clicks with a mouse, and a screen reader announces "Save, button." That announcement sets an expectation: the user hears "button" and reaches for Enter and Space, the way every button works. But a `<div>` isn't in the tab order and has no key handling, so it's dead to the keyboard. The `role` claimed something the markup can't deliver. The tempting fix is to stack on `tabIndex={0}`, an `onKeyDown` for Enter, another for Space, then recreate focus by hand, rebuilding `<button>` badly, attribute by attribute.
  </CodeVariant>

  <CodeVariant label="button (correct)">
    <div data-mark-color="green">

    ```tsx "button"
    <button onClick={save}>Save</button>
    ```

    </div>
    The native element brings the role, the keyboard, and focus together as one package, for free. The screen reader announces "Save, button," and Enter and Space genuinely work, because the browser wired them. ARIA gives you only the announcement; the native element gives you the announcement *and* the behavior, already in sync.
  </CodeVariant>
</CodeVariants>

This is why "semantic HTML first" from the previous lesson is not a style preference. Native elements are the only thing that keeps what AT *says* about a control and what the control *does* in lockstep. Split them, putting the role on one element and the behavior nowhere, and the announcement no longer matches reality.

This lesson is narrow on purpose. Native HTML and the shadcn primitives cover the baseline, leaving ARIA four jobs, and only four:

- **Roles** describe custom widgets. The primitive already writes almost all of them, so this is mostly a list of things you *don't* do.
- **Labels** give a name to a control with no visible text.
- **Descriptions** attach help or error text to a control.
- **Live regions** announce changes a sighted user would simply see.

The rest of the lesson covers each in order: the gap native HTML leaves, and the one ARIA tool that fills it.

## Roles: the few you write, the many the primitive owns

A `role` overrides an element's *semantics* for assistive technology: it tells AT to treat the element as something other than what its tag says. So when do you need to override the semantics HTML already gives you?

Rarely. Every HTML5 element ships an <Term definition={"The role an element already has, before you add any role attribute.\nA button element is implicitly a button, nav is a navigation landmark, main is the main landmark.\nA role attribute only matters when you need something different from the implicit one."}>implicit role</Term> for free: a `<button>` is already a button to AT, `<nav>` a navigation region, `<main>` the main region, `<h1>` a heading. An explicit `role="button"` on a `<button>` just repeats the element you already chose.

The complex roles, for tabs, menus, comboboxes, trees, and grids, **you do not write either.** A shadcn `DropdownMenu` is already wired as `menu` and `menuitem`, `Tabs` as `tablist`, `tab`, and `tabpanel`, `Dialog` as `dialog`. The Radix primitive underneath owns the whole role taxonomy for the widget; your job is to recognize that it is already handled, not to reproduce it.

That leaves a short list of roles a web app engineer actually authors:

- `role="status"` and `role="alert"`, for announcing live changes. These get their own section later.
- `role="presentation"` (or its synonym `role="none"`), which *strips* an element's implicit semantics. Use it when inherited markup reuses a semantic element purely for layout, such as a `<table>` laying out a form, and AT announces "table" over what is really visual scaffolding. The role tells AT to ignore the semantics and treat the element as a plain container.
- Landmark roles `banner`, `navigation`, `main`, and `contentinfo`, the explicit equivalents of `<header>`, `<nav>`, `<main>`, and `<footer>`. You met <Term definition={"A region of the page that AT users can jump straight to — banner, navigation, main, contentinfo, and a few more.\nThe HTML5 elements header, nav, main, footer provide them implicitly; the role attribute is the fallback when you can't use the element."}>landmark</Term> landmarks in the lesson on semantic structure. **Prefer the element;** reach for the `role` only when you genuinely cannot change the tag.

In each case the real fix is the *element*, and the `role` is the fallback for inherited code you can't restructure today:

<div data-mark-color="blue">

```tsx "role=\"presentation\""
{/* legacy layout table — presentation until it's rebuilt as a grid */}
<table role="presentation">
  {/* … inherited rows … */}
</table>
```

</div>

## Give every control an accessible name

Every interactive control needs an <Term definition={"The string assistive technology announces for a control.\nFor a button with text, it's the text. For an icon-only button, you supply it with aria-label or visually-hidden text.\nEvery interactive control needs a non-empty one."}>accessible name</Term>: the string AT announces when the user lands on it. A sighted user reads a button's name off its visible text, and AT needs that same name. The only question is where the name comes from. There are four sources, and one rule keeps them simple: **exactly one source supplies the name; you never stack them.** Stacked, they have a fixed override order, `aria-labelledby` over `aria-label` over visible text, but once you rely on that order you have already made the mistake. Supply one.

Here are the four sources, from the one you reach for first to the one you reach for last:

1. **Visible text content.** The default, and the best one. In `<button>Save</button>` or `<a href="/settings">Settings</a>`, the name *is* the visible text, so the two can never drift apart. When a control has visible text, you are done; add nothing.
2. **`aria-label`.** Supplies a name when there is *no* visible text to use. This is the icon-only button, coming up next.
3. **`aria-labelledby={id}`.** Borrows another element's text as the name. Reach for this when the label already exists on screen, such as a section named by its own heading. It pairs naturally with `useId` for the id.
4. **`title`.** Listed only so you know to *avoid* it for naming. The `title` attribute shows a tooltip on mouse hover, but AT support for it as a name is inconsistent, and it never reaches keyboard or touch users at all.

This chain is not about form inputs. A text input gets its name from a `<label htmlFor>`, the form-specific mechanism you met in the label-contract lesson, and that is the right tool for inputs. Don't reach for `aria-label` on an `<input>` when a visible `<label>` is what the field wants.

### The icon-only button

This case recurs in every modal, drawer, toast, and table row you build. You drop a close button into a dialog:

```tsx
<Button size="icon"><X /></Button>
```

To a sighted user this is obviously a close button, because the X says so. To a screen reader it announces, in full, "button." No name. The user has landed on a control with no idea what it does.

You might think the `<X />` needs an `aria-hidden` so the screen reader doesn't try to read the SVG. It doesn't: Lucide, the icon set shadcn ships, marks every icon `aria-hidden="true"` *by default*, so the glyph is already invisible to AT. The problem isn't that the icon is announced; it's that *nothing* is. The name has to go on the **button**, where the interaction lives, never on the icon. There are two equivalent ways to put it there:

<AnnotatedCode lang="tsx" code={`
<Button size="icon"><X /></Button>

<Button size="icon" aria-label="Close"><X /></Button>

<Button size="icon">
  <X />
  <span className="sr-only">Close</span>
</Button>
`}>
  <AnnotatedStep meta="{1}" color="red">
    The starting point. The Lucide `<X />` is already `aria-hidden`, so AT reads only the button's role and finds no name. The user hears "button" and nothing more.
  </AnnotatedStep>

  <AnnotatedStep meta={`"aria-label=\\"Close\\""`} color="green">
    The most direct fix. `aria-label` puts the name straight onto the interactive element, and the control now announces "Close, button." Reach for this in the common case.
  </AnnotatedStep>

  <AnnotatedStep meta="{7}" color="green">
    The equivalent alternative: real text content, hidden from view but present in the accessibility tree, so it becomes the button's name the normal way (source 1 in the chain). The result is identical, so pick whichever reads cleaner at the call site, and use this when you want the label as real DOM text rather than an attribute.
  </AnnotatedStep>
</AnnotatedCode>

That `sr-only` is a Tailwind utility: <Term definition={"A Tailwind utility that hides an element visually while keeping it in the accessibility tree, so screen readers still announce it.\nUsed for text that gives AT context a sighted user gets from layout or an icon.\nFull treatment in the next section."}>`sr-only`</Term> hides an element visually while keeping it in the accessibility tree. You'll see it again shortly; for now, read it as "text only AT can perceive."

Now put it into practice. The exercise below hands you a toolbar where every button is icon-only and nameless. Give each one an accessible name, and watch for the case the chain warns about: the one button that *does* have visible text needs nothing, so don't stack a redundant `aria-label` onto it.

## Help text and descriptions with `aria-describedby`

A name tells the user *what a control is*. A **description** tells them something *about* it: a format hint, a sentence of help text, an error message. AT reads it *after* the name. You wire it with `aria-describedby`, which works by reference: point the control at the id (or ids) of the elements holding the description text.

```tsx
const hintId = useId();

<input aria-describedby={hintId} />
<p id={hintId}>We'll never share your email.</p>
```

The attribute takes a space-separated list of ids, so one control can carry several descriptions, a hint and an error for instance, and AT reads each in turn. Above it points at one, so the input announces its name, then "We'll never share your email."

The id is the part worth pausing on, because hand-writing it invites a bug. A description lives in a separate element from the control that references it, so the two must agree on a string. Hard-code `id="email-hint"` and let that component render twice on the page, two copies of the form or a list of them, and now two elements share one id and the reference is ambiguous. `useId`, from the lesson on stable ids, hands you an id that is unique per instance *and* stable across the server render and client hydration, which is exactly what a cross-element reference needs.

<CodeTooltips tooltips={{
  useId: 'Returns a stable, unique string — the same value on the server render and the client, and different for every instance of the component.\nExactly what a cross-element id reference needs.',
}}>
```tsx
const hintId = useId();

<input type="email" aria-describedby={hintId} />
<p id={hintId}>We'll never share your email.</p>
```
</CodeTooltips>

One discipline to hold from the start: a reference and its target belong together. If the element a `describedby` points at gets emptied or removed while the attribute stays, AT reads an empty description or points at a node that no longer exists. Whenever you remove the hint, remove the reference in the same change.

This is the shallow version. Descriptions earn their keep in form validation, pairing `aria-describedby` with `aria-invalid` and announcing the error at the right moment, which the forms chapter (Chapter 44) builds properly. Here you only need the wiring: a referenced element, read after the name, held to the control by a `useId`-stable id.

## Hiding the right things from the right audiences

Three attributes hide content, and they are constantly confused, because "hidden" gets treated as one thing when it isn't. One question untangles all three: **who needs to perceive this content?** A piece of content can serve sighted users, AT users, both, or neither, and each case has its own tool.

- **`sr-only`** (the Tailwind utility): in the accessibility tree, off the screen. Visible to AT, hidden from sighted users. Use it for text that gives AT the context a sighted user already reads from layout or an icon: skip-link text, the icon-button label from two sections ago, a "Showing results for…" line.
- **`aria-hidden="true"`**: on the screen, out of the <Term definition={"The parallel tree assistive technology actually consumes, derived from the DOM.\nEach node carries a role, a name, a state. aria-hidden removes a node and its whole subtree from this tree.\nWhat AT announces is this tree, not the DOM directly."}>accessibility tree</Term>. Visible to sighted users, hidden from AT. Use it for purely *decorative* visuals that would be noise if announced: a decorative image, an icon sitting *next to* a visible text label.
- **`hidden` / `display: none`**: off the screen, out of the accessibility tree, out of layout. Hidden from everyone, because it isn't relevant to anyone right now: a collapsed accordion panel's body, a tab's contents while another tab is active.

Icons are where the three tools fall into place. Take `<Mail /> Send`, an icon beside the word "Send." The word carries the meaning; the icon is decoration. Announce both and the user hears "mail, Send," noise, so the icon should be `aria-hidden`, which Lucide does by default: a decorative icon next to a label needs nothing from you.

A *standalone* `<Mail />` button, an icon with no text, looks like it breaks that rule, since it clearly does something. So shouldn't you un-hide its icon? No. The resolution is the rule you already learned: don't expose the icon, **name the button** (`aria-label="Compose"`). The name lives on the interactive element, and the icon stays decorative in both cases. The icon being decorative and the control being meaningful are separate layers; separate them and the conflict disappears.

:::caution
One mistake here leaves users stuck: never put `aria-hidden="true"` on a focusable element, a button, link, or input, or on anything that *contains* one. `aria-hidden` removes the element from the accessibility tree but **not** from the tab order. Keyboard focus can still land there, and when it does, AT announces nothing, so the user reaches a control they can't hear. To make something gone, take it out of the DOM or make it genuinely inert; don't `aria-hidden` over a control the keyboard can still reach.
:::

## Live regions: announcing async UI changes

The fourth surface carries most of this lesson's machinery. Here is the problem it solves. A sighted user *sees* a toast slide in, a "Saved" badge flip on, or a result count change after they filter a table. An AT user perceives none of it: the page changed off to the side, silently, with nothing to announce it. A <Term definition={"A region of the DOM that assistive technology watches for changes.\nWhen its contents change, AT announces the new text — without the user moving focus there.\nThe mechanism for making async changes (toasts, save indicators, counts) perceivable."}>live region</Term> fixes this. AT *watches* it, so when its contents change, AT reads the new text aloud without the user moving focus there.

A live region is defined by a small set of attributes. The walkthrough below builds a minimal one, one attribute at a time.

<AnnotatedCode lang="tsx" code={`
<div aria-live="polite" aria-atomic="true">
  {message}
</div>

<div role="status">{message}</div>
`}>
  <AnnotatedStep meta={`"aria-live=\\"polite\\""`} color="blue">
    `aria-live` says *when* AT announces a change. `"polite"` waits until the user is idle, then reads it, the right choice for almost everything. `"assertive"` interrupts whatever AT is saying *right now*; reserve it for must-not-miss messages.
  </AnnotatedStep>

  <AnnotatedStep meta={`"aria-atomic=\\"true\\""`} color="blue">
    `aria-atomic` says *how much* to announce. `true` reads the whole region on any change; the default (`false`) reads only the node that changed. Use `true` when the message only makes sense whole: "Saved 3 of 5" means nothing if AT reads just the "5".
  </AnnotatedStep>

  <AnnotatedStep meta={`"role=\\"status\\""`} color="green">
    You rarely set those two by hand, because the roles bundle the right combination. `role="status"` implies `aria-live="polite"` and `aria-atomic="true"`; `role="alert"` implies `assertive` and atomic. Learn the two roles and you've learned the common cases, so reach for the role, not the raw attributes.
  </AnnotatedStep>

  <AnnotatedStep meta="{1-3}" color="orange">
    This is what the next diagram is about, and what breaks live regions most often: the region must already exist in the DOM *before* its content arrives. AT *monitors* registered regions for changes, so a region that mounts with its text already inside was never registered in time, and the change goes unheard.
  </AnnotatedStep>
</AnnotatedCode>

That last rule is subtle and broken often enough to be worth *watching* rather than just reading. AT announces a *mutation inside a region it is already watching*, not a region appearing, so the order of operations matters in a way the rendered output hides. Scrub through the sequence below, which shows AT's point of view over time for two implementations side by side: one that always mounts the region empty, and one that conditionally renders it.

<DiagramSequence>
  <DiagramStep>
    <PreMountRule step={1} />
    <Fragment slot="caption">
      **Mount.** The always-mounted region renders empty, so it's in the DOM and AT *registers it and starts watching*. The conditional version renders nothing while `msg` is falsy, so there's no region to watch yet. Both are silent, but the whole difference is settled right here, before any text exists.
    </Fragment>
  </DiagramStep>

  <DiagramStep>
    <PreMountRule step={2} />
    <Fragment slot="caption">
      **`setMsg('Saved')`.** On the left, "Saved" is inserted *into the region AT was already watching*, so AT detects the mutation and announces it. On the right, `msg` turns truthy, so the region mounts *with "Saved" already inside it*. AT sees a brand-new node appear, not a change in a watched region, so it stays silent (or fires unreliably). Same text on screen, but only one is heard.
    </Fragment>
  </DiagramStep>

  <DiagramStep>
    <PreMountRule step={3} />
    <Fragment slot="caption">
      **`setMsg('Saved ✓')`.** Every later change to the watched region is announced too, so it keeps working. The conditional region now exists, but it was never registered, so its updates stay unreliable. Announcement keys off a mutation *inside a region AT already watches*, not a region that appears with text already in it.
    </Fragment>
  </DiagramStep>
</DiagramSequence>

The fix follows straight from the diagram: always render the region, and toggle only its *contents*. The two versions sit one keystroke apart, and that keystroke is the whole bug.

<CodeVariants>
  <CodeVariant label="Broken — conditional render">
    <div data-mark-color="red">

    ```tsx {1}
    {error && <div role="alert">{error}</div>}
    ```

    </div>
    The region only exists when `error` is truthy, so it mounts *with the text already inside*, and AT was never watching it. Sighted users see the error; no one hears it. This is the most common shape of the live-region bug.
  </CodeVariant>

  <CodeVariant label="Fixed — always-mounted region">
    <div data-mark-color="green">

    ```tsx "role=\"alert\""
    <div role="alert">{error}</div>
    ```

    </div>
    The region is always in the DOM, and only its *contents* toggle (empty when `error` is falsy). AT registered it on mount, so when `error` fills it, AT announces the change. Same markup, only the timing reordered, and now it works.
  </CodeVariant>
</CodeVariants>

### `status` or `alert`?

The two roles split on one axis: **`alert` interrupts, `status` waits.** `alert` cuts into whatever AT is currently reading, every time, which is right for a genuine time-sensitive failure and wrong for routine confirmations. Wire your "Draft saved" badge as `alert` and the screen reader cuts off the user's reading every few seconds. The split is about severity:

- **`role="status"`** is the default reach, for anything informational: "Saving…", "Draft autosaved", "Search returned 12 results", "Copied to clipboard."
- **`role="alert"`** is reserved for time-sensitive failures the user must not miss: "Session expired", "Payment failed", "Connection lost."

When in doubt, use `status`. `alert` is the exception you justify, not the default you reach for.

### Sonner builds the toast's live region for you

Here is the payoff for all that machinery: most of the time, you get to *not* build it. The most common live region in any SaaS app is the toast, and shadcn's default toast is <Term definition={"shadcn/ui's default toast library since 2026 (it replaced the deprecated built-in Toast component).\nIt mounts one persistent live region at the app root and injects toast content into it, so the pre-mount rule is satisfied for you."}>Sonner</Term>. Sonner renders **one persistent live region at the app root** and injects every toast's content into it. So the pre-mount rule, the whole diagram you just scrubbed through, is already handled: the region is always mounted, and Sonner mutates its contents.

Your job narrows to the one piece of judgment that's actually yours: picking the severity.

```tsx
toast.success('Saved');
toast.error('Payment failed');
```

The severity you pick is the politeness you get: a confirmation announces calmly, a failure with the urgency it deserves. You learned the machinery not to hand-build a toast, but to trust the primitive that did, and to build the live region yourself when the surface isn't a toast and no primitive covers it.

That last case, a live region you build by hand, comes up more than you'd expect. Here is where it shows up in a real SaaS UI:

- **Toasts** use Sonner, handled as above.
- **A search or filter result count** is a `role="status"` in the results header, updated after a filter runs: "Showing 12 of 134". This is the canonical one you build yourself, since no primitive covers "the list changed, tell AT how many."
- **An optimistic save indicator** is a "Saved" badge as `role="status"` when the optimistic update lands, and a `role="alert"` on rollback: "Couldn't save, changes reverted."
- **An inline form error** is a `role="alert"` beside the field, populated when validation fails.

Recognize the pattern and you'll spot every place a live region belongs, reaching for one only where the primitive doesn't already cover you.

## The four surfaces, together

Native HTML and the shadcn primitives are the baseline; they handle most of accessibility before you write a single `aria-` attribute. ARIA is the narrow slice on top, and it is exactly four jobs:

- **Roles** are almost always the primitive's, not yours. *Trigger: a custom widget no semantic element or primitive covers (rare). Mostly `presentation` to strip inherited layout semantics, or landmarks when you can't change the tag.*
- **Labels** are yours, on controls with no visible text. *Trigger: an icon-only button. The name goes on the control, never the icon.*
- **Descriptions** are yours, for help and error text. *Trigger: an input that needs a hint or an error read after its name. Wire it with `aria-describedby` and a `useId` id.*
- **Live regions** are yours, for async state a sighted user would just see. *Trigger: a toast, a result count, a save indicator. Mount the region first; prefer `status` over `alert` unless it's a genuine, must-not-miss failure.*

Carry one habit into every screen: before you add any `aria-*`, ask whether a native element or your shadcn primitive already does this. If it does, that's the bug, so fix the markup instead of adding the attribute. Asked every time, that question is what separates the pages averaging 42 WebAIM errors from those averaging 59. No ARIA is better than bad ARIA.
