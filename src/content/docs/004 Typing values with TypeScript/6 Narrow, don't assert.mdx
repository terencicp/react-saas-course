The previous lesson left a problem open: a field that lives only on `User` can't be read off a `User | Guest`, because the compiler doesn't know which variant you hold. The fix was a runtime check, `'email' in value`. This lesson covers the full set of those checks and the rule behind them.

Skipping the check looks tempting:

<div data-mark-color="red">

```ts "value as User"
const getEmail = (value: User | Guest): string => {
  return (value as User).email;
};
```

</div>

The `as User` tells the compiler "trust me, this is a `User`." It compiles and ships. Months later a `Guest` flows through, `value.email` is `undefined`, and the next line that reads it crashes, unflagged.

A <Term definition="A compile-time-only operation that tells the type checker to treat a value as a different type. It has no runtime effect — the value is unchanged. The check the type system would have made is silenced; the developer takes responsibility for the claim.">type assertion</Term> changes nothing at runtime; it only stops the compiler from checking. Do the opposite: write a check the language can read, and let it carry the resulting type into the block.

## How TypeScript narrows types from runtime checks

TypeScript reads a function body top to bottom, branch by branch. When it meets a runtime check on a value, it refines that value's type along each path: inside `if (typeof x === 'number')`, it treats `x` as `number` in the `if` branch and as the remaining union members in the `else`. The check runs at runtime, the refinement happens at compile time, and the feature tying them together has a name: <Term definition="The TypeScript feature where the compiler tracks how runtime checks on a value refine its type along each branch of control flow. A check like typeof x === 'number' narrows x to number inside the if and to the remaining union members in the else.">control-flow narrowing</Term>. The checks that drive it are `typeof`, `in`, and `===` on a discriminant; the lesson works through each.

One rule captures the whole lesson:

> **Narrow with a runtime check the language tracks. Never assert past a union without one of three named triggers.**

A narrowing check is sound: the compiler reads code that actually runs and carries forward a fact it has seen hold. An assertion gives it nothing to observe, so it takes the developer's word instead. Narrowing is the default; the assertion is an escape hatch for the three cases named later.

## The narrowing forms and when to use each

TypeScript has six core narrowing forms. The set is small, so at each union read the question is "which form fits?" not "should I cast?"

<CodeVariants>
  <CodeVariant label="typeof">
    <div data-mark-color="green">

    ```ts "typeof amount === 'number'"
    const formatAmount = (amount: string | number): string => {
      if (typeof amount === 'number') {
        return amount.toFixed(2);
      }
      return amount.trim();
    };
    ```

    </div>
    **`typeof` for mixed primitives.** Use it when the union mixes primitive types; the matched branch narrows to that primitive, the `else` to the rest.
  </CodeVariant>

  <CodeVariant label="Equality on a literal">
    <div data-mark-color="green">

    ```ts "status === 'draft'"
    type Status = 'draft' | 'sent' | 'paid';

    const canEdit = (status: Status): boolean => {
      if (status === 'draft') {
        return true;
      }
      return false;
    };
    ```

    </div>
    **Equality on a literal union.** Use `===` against a literal when the union is a finite set of literals; the branch narrows to the literal you tested. The discriminated-union switch below runs on this same mechanism, since a discriminant is just a shared literal-typed field.
  </CodeVariant>

  <CodeVariant label="in">
    <div data-mark-color="green">

    ```ts "'email' in value"
    const getEmail = (value: User | Guest): string => {
      if ('email' in value) {
        return value.email;
      }
      return 'no-reply@example.com';
    };
    ```

    </div>
    **`in` for shape unions.** Use it, as the previous lesson did for `User | Guest`, when object variants share no discriminant but one owns a field the others lack; the branch narrows to that variant.
  </CodeVariant>

  <CodeVariant label="instanceof">
    <div data-mark-color="green">

    ```ts "error instanceof ValidationError"
    try {
      await saveInvoice(input);
    } catch (error) {
      if (error instanceof ValidationError) {
        return showFieldErrors(error.fields);
      }
      throw error;
    }
    ```

    </div>
    **`instanceof` for class branches.** Use it to branch on which class produced a value; the check reads the prototype chain and narrows to that class. The usual case is a `catch` block, whose binding is `unknown`. One caveat: `instanceof` is unreliable across <Term definition="A separate JavaScript execution context with its own set of global objects and built-in constructors, such as an iframe or a web worker. A value created in one realm fails an instanceof check against a constructor from another, because the two realms have different constructor objects.">realm</Term> boundaries like an iframe or worker, where each realm has its own `Error` constructor.
  </CodeVariant>

  <CodeVariant label="Array.isArray">
    <div data-mark-color="green">

    ```ts "Array.isArray(input)"
    const normalize = (input: string | string[]): string[] => {
      if (Array.isArray(input)) {
        return input;
      }
      return [input];
    };
    ```

    </div>
    **`Array.isArray` for `T | T[]` unions.** Use it when the union is a value or a list of it. It needs its own form because `typeof` reports both arrays and plain objects as `'object'`.
  </CodeVariant>

  <CodeVariant label="switch on a discriminant">
    <div data-mark-color="green">

    ```ts "r.status" "case 'loading':" "case 'success':" "case 'error':"
    type FetchResult<T> =
      | { status: 'loading' }
      | { status: 'success'; data: T }
      | { status: 'error'; error: Error };

    const render = <T>(r: FetchResult<T>): string => {
      switch (r.status) {
        case 'loading':
          return 'Loading...';
        case 'success':
          return JSON.stringify(r.data);
        case 'error':
          return r.error.message;
      }
    };
    ```

    </div>
    **`switch` on a discriminant.** When shapes share a literal-typed field, as in the previous lesson's `FetchResult<T>`, switching on it narrows each `case` to its variant. That field is the <Term definition="A literal-typed field that appears on every variant of a union, with a different literal value per variant. Narrowing on the discriminant separates the variants at compile time.">discriminant</Term>. The `default` branch holds the exhaustiveness check, the `assertNever` pattern the next chapter builds, which catches a forgotten variant when the union grows.
  </CodeVariant>
</CodeVariants>

A seventh form is worth recognizing: the **custom type predicate**. When a check is too involved to inline at every use site, or needs reuse across modules, package it as a function whose return type tells the compiler "I have verified this fact."

<div data-mark-color="blue">

```ts "value is User"
function isUser(value: unknown): value is User {
  return (
    typeof value === 'object' &&
    value !== null &&
    'email' in value &&
    typeof value.email === 'string'
  );
}
```

</div>

The `value is User` return type is a <Term definition="A function whose return type is `value is T`. When the function returns true, TypeScript narrows the argument to T at the call site. The predicate is only as honest as its body — the compiler trusts the signature.">type predicate</Term>. When `isUser(x)` returns `true`, the compiler narrows `x` to `User` at the call site. It is only as honest as its body: a predicate that returns `true` on a non-`User` slips through, because the compiler trusts the signature, not the body. The next chapter covers the assertion-function form `asserts value is T`.

:::note
Type predicates must use `function`, not arrow form: the `value is T` signature works only on `function`. It's the one exception to the project's "arrows by default" rule.
:::

## Where a narrow holds

> **A narrow holds inside the block where the check fired, and any assignment that could change the type cancels it.**

This bites when a callback captures a narrowed value, because the variable could be reassigned between the check and the moment the callback runs.

<div data-mark-color="green">

```ts {3}
const handle = (value: User | Guest) => {
  if ('email' in value) {
    const user = value;
    queueMicrotask(() => sendEmail(user.email));
  }
};
```

</div>

The fix is the line after the check: `const user = value`. It captures the narrow while it holds, and the type system reads `user` from then on. Because `user` can't be reassigned, a later assignment to `value` can't reach through it.

:::note
Under strict TypeScript, a function call between the check and the read also drops the narrow, since the compiler can't prove the call didn't reassign the variable through a closure. The same `const` capture fixes it.
:::

## The three legitimate triggers for `as`

`as` has exactly three legitimate triggers; anything outside them is a signal to refactor. The file below uses each once.

<AnnotatedCode lang="ts" code={`
  import { z } from 'zod';

  const userSchema = z.object({
    id: z.string(),
    email: z.string().email(),
  });

  type User = z.infer<typeof userSchema>;

  const parseUser = (raw: unknown): User => {
    return userSchema.parse(raw);
  };

  const cache = new Map<string, User>();

  const remember = (user: User): User => {
    cache.set(user.id, user);
    return cache.get(user.id) as User;
  };

  const wireUpSubmit = () => {
    const submit = document.querySelector('button[type="submit"]') as HTMLButtonElement;
    submit.addEventListener('click', () => parseUser({}));
  };
`}>
  <AnnotatedStep meta={`"userSchema.parse(raw)"`} color="green">
    **Boundary parse-then-trust.** A validator reads an `unknown` at the boundary, checks it at runtime, and returns a typed value. The assertion lives inside the parser's return type, so your own code writes no `as`.
  </AnnotatedStep>

  <AnnotatedStep meta={`"cache.get(user.id) as User"`} color="orange">
    **TypeScript can't see what you can prove.** You just stored a `User` under `user.id` and read it straight back, but `cache.get` returns `User | undefined` because the `Map` API must allow for misses. Before asserting, ask whether a refactor removes the gap; often returning the value you just set does. When it can't, the assertion is acceptable.
  </AnnotatedStep>

  <AnnotatedStep meta={`"as HTMLButtonElement"`} color="violet">
    **The DOM and third-party type gaps.** `querySelector` returns `Element | null` because it can't infer a tag from your selector, but you can: it says "button," and you wrote the markup. For a tightly scoped one-shot the assertion is fine; if the value flows further, use `instanceof HTMLButtonElement`, a runtime check the compiler reads.
  </AnnotatedStep>
</AnnotatedCode>

**`as unknown as T` is a smell.** Stacking two assertions through `unknown` fully silences the type system. Occasionally that's right (a test fixture, a third-party boundary with no honest signatures), but usually it's a signal to refactor.

**Type assertions don't validate at runtime.** `value as User` compiles and changes nothing at runtime, so the next line that reads a `User`-only field on a `Guest` crashes. When the data may not match the type, narrow, don't assert.

## `!` is `as` for null and undefined

The non-null assertion `!` tells the compiler a value isn't `null` or `undefined`, with no runtime check.

Its most common honest use:

<div data-mark-color="orange">

```ts "!"
const ids = ['a', 'b', 'c'];
const target = ids.find((id) => id === 'b')!;
```

</div>

`find` returns `T | undefined`, but you wrote the array and the predicate, so you hold proof the type system can't track.

The alternative names the failure:

<div data-mark-color="green">

```ts "?? throwError('missing id b')"
const target = ids.find((id) => id === 'b') ?? throwError('missing id b');
```

</div>

`?? throwError(...)` gives the production error a string a log scanner can grep for. Reach for `!` in a one-shot script, a test fixture, or where the line carries the proof itself; reach for `?? throwError(...)` when the failure could reach production.

Index access works the same way. Under `noUncheckedIndexedAccess`, `arr[0]` is `T | undefined` even on a non-empty array, so `!` is acceptable under the same three triggers as `as`. Otherwise narrow with `if (arr.length > 0)` and capture the value, or keep the `| undefined` and handle the miss.

## Narrowing nullable values

Both `?` (field may be absent) and `| undefined` (present but `undefined`) narrow with the forms you've seen, with one gotcha.

<CodeVariants>
  <CodeVariant label="Truthy check">
    <div data-mark-color="green">

    ```ts "if (user)"
    const greet = (user: User | null): string => {
      if (user) {
        return `Hello, ${user.name}`;
      }
      return 'Hello, guest';
    };
    ```

    </div>
    **Truthy check.** A bare `if (user)` is correct for `User | null`: the object is truthy, `null` is falsy. The gotcha is broader. A <Term definition="An if (x) check that branches on whether the value is truthy. The falsy values in JavaScript are false, 0, '', null, undefined, NaN, and 0n — a truthy check excludes all of them, not just null/undefined.">truthy check</Term> on `string | number | null | undefined` also excludes `0`, `''`, and `false`, which you usually want to keep. There, use `!= null`: since `null == undefined`, one comparison catches both, and it's a rare legitimate use of double-equals.
  </CodeVariant>

  <CodeVariant label="Nullish coalescing">
    <div data-mark-color="green">

    ```ts "?? 'guest'"
    const name = user?.name ?? 'guest';
    ```

    </div>
    **`??` for default and continue.** Not a narrow, but the right reach to supply a default and continue in one expression. `??` triggers on `null` and `undefined` only, never on `0`, `''`, or `false`. Use it when the value flows straight into a use; use an explicit check when the branches do different things.
  </CodeVariant>

  <CodeVariant label="Optional chaining gotcha">
    <div data-mark-color="green">

    ```ts "if (!user) return null" "user.name" "user.email"
    const greetAndEmail = (user: User | null): string | null => {
      if (!user) return null;
      return `${user.name} <${user.email}>`;
    };
    ```

    </div>
    **`?.` short-circuits, it doesn't narrow.** Optional chaining short-circuits at runtime: if `user` is `null`, `user?.email` is `undefined` without reading `.email`. But it doesn't narrow `user`, so its type outside the expression is unchanged. When several reads follow, narrow once with an early return, then read directly.
  </CodeVariant>
</CodeVariants>

## Practice: rewrite an assertion-heavy function

The function below carries two `as` assertions, each removed a different way.

  starter={`type User = {
  kind: 'user';
  id: string;
  email: string;
};

type Guest = {
  kind: 'guest';
  id: string;
};

type Role = 'admin' | 'member';

const roleLabels: Record<Role, string> = {
  admin: 'Administrator',
  member: 'Member',
};

// Refactor: replace both \`as\` assertions with narrowing.
const describe = (value: User | Guest, roleKey: string): string => {
  const email = (value as User).email; // smell: asserts past a union
  const role = roleLabels[roleKey as Role]; // smell: asserts a wider type into a narrower one
  return \`\${email} (\${role})\`;
};

// Pin the narrowing patterns. Replace each \`false\` with a runtime check;
// the ^? queries must resolve to the narrowed types.

declare const v: User | Guest;
if (false /* narrow v so v.email is allowed */) {
  const probe = { email: v.email };
  //    ^?
}

declare const k: string;
if (false /* narrow k so roleLabels[k] is allowed */) {
  const narrowedKey = k;
  //    ^?
  const label = roleLabels[k];
}

// These must continue to fail to type-check:

## Sort each scenario: narrow or assert?

<Buckets twoCol instructions="For each union read below, decide whether a narrowing check is available or whether the read sits at one of the three legitimate assertion triggers.">
  <Bucket name="narrow" label="Narrow with a runtime check" description="The language gives you a check it can track" />
  <Bucket name="assert" label="Assertion is acceptable here" description="Boundary parse, proof gap, or DOM seam" />

  <Item bucket="narrow">A parameter typed `string | number` that needs to format as currency for numbers</Item>
  <Item bucket="narrow">A `User | Guest` value where only `User` has an `email` field</Item>
  <Item bucket="narrow">A `FetchResult<T>` discriminated on `status`</Item>
  <Item bucket="assert">A `parsed = userSchema.parse(payload)` where `payload` was `unknown`</Item>
  <Item bucket="assert">A `document.querySelector('button[type="submit"]')` call in a tightly-scoped one-shot</Item>
  <Item bucket="narrow">An `error` value inside a `catch (error)` block</Item>
  <Item bucket="assert">A `map.get(id)` immediately after `map.set(id, user)`</Item>
  <Item bucket="narrow">A `User | null` returned from a database lookup before reading `.email`</Item>
</Buckets>

The rule for code review: **narrow with the language, and reach for `as` only at the boundary, the proof gap, or the DOM seam.**
