A user types 280 emojis into a bio field with a "280-character limit" and gets a "too long" error. Another signs up with an accented letter in their name, and the duplicate check misses a row that looks identical on screen. Both bugs trace to one fact: JavaScript's `string.length` counts UTF-16 storage units, not the characters a user perceives. This lesson covers which of the three counts to use, and how to compare two strings a user sees as identical.

The lesson here goes beyond "watch out for emojis." `.length` is a <Term definition={"A property of how the value is stored or transmitted, not of what the value represents. `.length` reports the storage form, not the human-meaningful count."}>serialization detail</Term>: it reports how the engine stored the string, not how a human reads it. The rest of this lesson covers the three counts you actually have, and how to pick the right one.

## Code units, code points, and grapheme clusters

JavaScript has no single "length of a string." It has three, and each answers a different question. So instead of "how long is this string?", ask "do I need code units, code points, or <Term definition={"One character as the user perceives it on screen. Can span multiple Unicode code points — a base letter plus combining marks, an emoji built from a zero-width-joiner sequence, a regional-indicator pair forming a flag."}>grapheme clusters</Term>?"

Start with the same input measured all three ways:

```ts
const family = '👨‍👩‍👧‍👦';

family.length;                                            // 11
[...family].length;                                       // 7
[...new Intl.Segmenter('en', { granularity: 'grapheme' })
  .segment(family)].length;                               // 1
```

When to reach for each:

- **Code units**: `string.length`. The right answer when the value is a key, an index back into the same string, or a byte budget for a serialized payload. Fast and correct for ASCII, but wrong for anything the user sees.
- **Code points**: `[...string].length` (or `Array.from(string).length`). Spreading a string iterates by Unicode code point, so surrogate pairs collapse to one. Closer to what a human would count than `.length`, but still wrong for any character built from joined sequences. The family above is *seven* code points but one cluster on screen.
- **Grapheme clusters**: `new Intl.Segmenter(locale, { granularity: 'grapheme' })`, then count the segments. The right answer for "how many characters does the user see," and what a length check on a user-facing field should use.

Each step up in fidelity, from code units to code points to grapheme clusters, handles another class of input the cruder count gets wrong. On ASCII all three agree, which is why `.length` looks fine on `'hello'` and then fails without warning the moment a user pastes an emoji or an accented character.

## `Intl.Segmenter`: counting perceived characters

`Intl.Segmenter` is part of the platform baseline, so on the course's Node 24 LTS you can use it directly: no polyfill, no feature check, no fallback.

The one-liner to memorize:

```ts
const countCharacters = (input: string): number =>
  [...new Intl.Segmenter('en', { granularity: 'grapheme' }).segment(input)].length;

countCharacters('🇺🇸');         // 1
countCharacters('👨‍👩‍👧‍👦');     // 1
countCharacters('café');        // 4
```

The constructor takes a **locale** and a **granularity**. The locale matters for scripts where grapheme rules differ (Thai, Khmer, Devanagari); for English and most Latin-script text the cluster boundaries come out the same, but you still pass one. `'grapheme'` segments by user-perceived character; the same constructor also supports `'word'` and `'sentence'`.

`.segment(input)` returns an iterable of `{ segment, index, ... }` objects, one per cluster. The result has no `.length` or `.size`, so the idiomatic count is to spread it into an array and read its length.

The companion granularities are worth recognizing even if you rarely reach for them. `'word'` is the tool for word-count features, and each segment carries an `isWordLike` flag so you can skip punctuation and whitespace; `'sentence'` does the same for sentence counts. Both are rare in SaaS UIs, but together they make `Intl.Segmenter` the one tool that handles all three jobs.

:::caution
Never truncate a user-facing string at an arbitrary character index. `'👨‍👩‍👧‍👦'.slice(0, 5)` cuts through the middle of the family emoji's code-point sequence and produces broken Unicode, the mojibake "broken character" boxes the renderer shows in its place. When a field needs a hard limit (preview text, an SMS body, a card heading), iterate the segments and concatenate them up to the limit.
:::

The same `Intl.*` namespace also ships `Intl.NumberFormat` (from the previous lesson on money), `Intl.Collator` for locale-aware sorting, and `Intl.DateTimeFormat` for dates and times. This is the platform-native internationalization surface the course leans on instead of third-party libraries.

## Normalization at the storage boundary

Two strings can look identical on screen yet compare as different. Here the two literals render the same, but the equality check fails and the two length checks disagree:

```ts
const a = 'café';            // precomposed: 'c', 'a', 'f', 'é'
const b = 'café';            // decomposed:  'c', 'a', 'f', 'e' + combining acute
a === b;                     // false
a.length;                    // 4
b.length;                    // 5
```

A user types these as the same word, but they are different sequences of Unicode code points. The first uses a single precomposed `é`, one code point that already includes the accent. The second uses a plain `e` followed by a combining acute accent, two code points the renderer overlays into one visual cluster. For primitives, `===` compares the value byte for byte, and the bytes here genuinely differ.

The fix is one method call:

```ts
a.normalize('NFC') === b.normalize('NFC');   // true
```

`.normalize('NFC')` collapses both forms to the same canonical sequence. `NFC` stands for **Normalization Form C** (Canonical Composition): it combines characters into their precomposed form wherever possible. It's the form you want by default for storage, comparison, and search.

There are four normalization forms, and you only need a short rule of thumb for each:

- **`NFC`** (Canonical Composition): combine characters into their precomposed form. The default for storage, comparison, and search.
- **`NFD`** (Canonical Decomposition): split precomposed characters into base letter plus combining marks. Useful for accent-insensitive search, where you decompose and then strip the combining marks.
- **`NFKC`** / **`NFKD`** (Compatibility forms): collapse characters that look similar but are semantically distinct, so the `ﬁ` ligature becomes `fi` and full-width digits become ASCII digits. Useful for fuzzy matching at a search boundary, but the wrong default for storage because they lose information.

The rule that keeps this maintainable: **normalize once, at the database write boundary.** Don't sprinkle `.normalize('NFC')` at every `===` and `.length` downstream. If every value in the table is already NFC, every comparison and length check works against a canonical form for free. Put normalization at the same boundary that validates input (where Zod lands in a later unit): one call, in one place. If you catch yourself reaching for `.normalize` inside a comparison helper or search function, walk back to the seam where the value entered the system and normalize it there instead.

Drizzle's `text` and `varchar` columns don't normalize for you; Postgres stores whatever bytes you hand it. The normalization belongs in the schema or the action handler, before the row hits the database.

## `String.prototype`: what to use and what to recognize

`String.prototype` is huge and mostly legacy. You reach for a small set of methods daily and only need to recognize the long tail when you meet it in older code. The working surface:

- **`includes`** / **`startsWith`** / **`endsWith`**: substring tests. Prefer these to `indexOf(needle) !== -1`, which asks "where is it?" when you only mean "is it there?"
- **`at(-1)`**: last-character access, cleaner than `string[string.length - 1]`. Negative indices count back from the end at any position.
- **`slice(start, end)`**: substring extraction, and the default choice. Prefer it to `substring` (which silently swaps its arguments when `start > end`) and `substr` (deprecated).
- **`split`** / **`join`**: the boundary between a string and an array of segments, always paired. `split(sep)` breaks the string apart; `join(sep)` reassembles it.
- **`replaceAll(needle, replacement)`**: replaces every occurrence of a literal string, with none of the `replace(/needle/g, ...)` regex boilerplate.
- **`trim`** / **`trimStart`** / **`trimEnd`**: whitespace cleanup at input boundaries. Pair with the empty-string guard from the previous lesson when converting form input.
- **`padStart`** / **`padEnd`**: fixed-width formatting. Rare in SaaS UIs, occasional in logs and CLI output.
- **`localeCompare(other, locale, options)`**: locale-aware comparison, the right answer for any user-visible alphabetical sort. `<` and `>` compare by code unit, which puts accented characters where no reader would call them alphabetical.
- **`normalize(form)`**: the boundary tool from the previous section.

The legacy surface appears in older code and AI suggestions but earns no place in new code:

- **`substr`**: deprecated; like `slice`, but with a length instead of an end index. Use `slice`.
- **`substring`**: older sibling of `slice` that silently swaps its arguments when `start > end`. No reason to prefer it.
- **`escape`** / **`unescape`**: globals grouped with these methods by habit. Deprecated for over two decades; use `encodeURIComponent` / `decodeURIComponent` to escape URLs.
- **`String.prototype.bold`** / **`italics`** / **`fontcolor`** / etc.: 1990s HTML-wrapping methods, deprecated; JSX owns markup in this stack.
- **`String.raw`**: the template-literal escape hatch. Not legacy; it belongs to the next lesson, where tagged templates get full treatment.

Skim this once so you recognize each method on sight later. No need to memorize a reference; MDN has the complete surface when you want it.
