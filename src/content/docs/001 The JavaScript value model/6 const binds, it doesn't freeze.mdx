A teammate ships `const config = { feature: true }` at the top of a module and treats the value as protected. Another module imports `config` and sets `config.feature = false` mid-request to short-circuit a code path, and the flag flips silently for every request in flight. `const` did nothing wrong: it never promised to freeze the value, only that the *name* would keep pointing at the same object.

A different week, a different bug. A binding declared `let` "just in case" six months ago, never reassigned since, finally gets reassigned by an unrelated change. Downstream code had read the original value once and assumed it would hold still. Both bugs share one root: a misunderstanding of what `const` promises, and a habit of reaching for `let` when nothing needs it.

One rule closes both bug classes. Recall the binding diagram from the first lesson of this chapter: `const` locks the arrow, not the box.

## `const` blocks reassignment, not mutation

`const` is a <Term definition="A name that points to a value. In `const x = 1`, `x` is the binding; `1` is the value.">binding</Term> that cannot be **reassigned**. It says nothing about whether the **value it points at** can be mutated. Those are two different promises, and `const` makes only the first.

<BindingDiagram />

`const` makes the arrow permanent: you can't repoint it. The box at the other end is a different story. If the value there is mutable (and every object, array, `Map`, `Set`, and class instance is), any code holding a reference can reach in and change its contents. The arrow stays put; the box changes underneath.

```ts
const config = { feature: true };
config.feature = false;
// config = { feature: false };
```

The second line works. It mutates through the existing arrow, reaching into the object to change a property, and `const` has nothing to say about that. The third line, uncommented, would throw `TypeError: Assignment to constant variable.`: it repoints the arrow at a *different* object, and that reassignment is exactly what `const` blocks.

For a primitive, the distinction collapses. A primitive has no inside to mutate, so there's no way to change the contents of `42` or `'hello'`. `const x = 42` does behave as if the value were frozen, only because the value can't be mutated at all. The "`const` means a frozen value" model holds for primitives and breaks the moment the value is an object. That's where the bugs come from: the model that worked for `const PORT = 3000` quietly fails on `const config = { feature: true }`.

The defense isn't `Object.freeze`. It's the immutability habit from the first lesson of this chapter: copy then modify with spread or `structuredClone`. For now, hold onto the rule: **the arrow is locked, the box is not.**

## `const` by default, `let` when the binding must change

Write `const` for every binding unless the binding genuinely has to be reassigned. The trigger is not "the value might change," because `const` fixes the binding, not the value the binding holds. The trigger is the *binding itself* having to point at something different later. That is the only reason to use `let`.

In practice, `let` is justified in a small set of cases:

- An **accumulator** in a manual loop, such as a `let total = 0;` you increment as you walk a list. The binding reassigns on every iteration. (When the shape fits, `.reduce` avoids the mutable binding entirely.)
- A **value assigned in a branch** too complex for a ternary: `let role; if (...) { role = 'admin'; } else if (...) { role = 'editor'; } else { role = 'viewer'; }`. This is rare, and usually a sign the branches should move into a helper that returns the value, so the call site becomes `const role = pickRole(...)` again.
- A **loop counter** in a classic `for (let i = 0; ...; i++)`. It comes up less often than you'd expect, because `for...of`, `.map`, `.filter`, `.reduce`, and `Array.from({ length })` cover most cases, but it's a legitimate `let` when the index is genuinely what you need.

That list is exhaustive. Outside those shapes, if you wrote `let` and never reassigned, change it to `const`. You don't have to enforce this by hand: Biome's `useConst` rule, enabled in the chapter's `biome.json` since Unit 1, flags the pattern at build time and names the exact `let` to convert. Building the habit as a reading skill still pays off, because review happens before the lint runs: when you see a `let`, ask immediately where it gets reassigned.

Here is the same accumulator in three forms: the one to leave behind, the acceptable manual fallback, and the default to prefer.

The pattern across the three tabs is the chapter's binding rule at the keyword level. Prefer the most constrained form: `const` plus a method that needs no mutation. Fall back to the next step up, `let` plus a manual loop. Keep `var` for code you're rewriting, never for code you're authoring. Apply that ordering to every binding decision and reviewing your own code gets far easier.

## Block scope and the Temporal Dead Zone

Two mechanical rules sit underneath `const` and `let`, and they're linked tightly enough to learn together. The first is **block scope**: every `const` and `let` binding is scoped to the nearest pair of curly braces enclosing it, whether that's a function body, an `if` branch, a `for` loop, an arrow-function body, or a bare `{ ... }` block. The scope is **lexical**: it's determined by where the binding is written, not by the call stack that reaches it at runtime.

```ts
if (user.isAdmin) {
  const tier = 'pro';
  console.log(tier);
}

// console.log(tier); // ReferenceError — tier is not visible out here
```

The binding lives inside its block and nowhere else. `var` is the exception: because it's function-scoped, a `var` declared inside an `if` block leaks out to the surrounding function. That's the legacy bug class block scope was designed to eliminate.

The second rule stops a different bug class. Every `const` and `let` binding enters the <Term definition="The period between entering a scope and reaching a let/const declaration. The binding exists (the parser saw it) but accessing it throws a ReferenceError.">Temporal Dead Zone</Term> (TDZ) the moment its scope starts, and stays there until the line that declares it runs. While a binding is in the TDZ, the *name* exists, since the parser has already seen the declaration, but **accessing it throws a `ReferenceError`** rather than returning a value.

This closes an old `var` hazard. With `var`, accessing the binding before its declaration silently returned `undefined`, so a typo or a misordered statement gave you `undefined` at runtime instead of an error. That `undefined` then propagated until it surfaced somewhere unrelated. The TDZ makes the same access fail at the moment the bad code runs, which is the cheapest moment to fix it.

The fix isn't to swap to `var` to make the error go away; it's to declare the binding before you use it. That points to a habit worth building now: **declare bindings at the top of the scope where they're used**. Then anyone scanning a function top-down sees every declaration before its first use, and you rarely have to think about the TDZ again.

The mechanism underneath all of this is <Term definition="The compile-time process where the engine collects every name in a scope and pre-registers it before any code runs. For `var`, the name is initialized to `undefined`; for `let`, `const`, and `class`, the name is registered but unreachable until the declaration line (the TDZ).">hoisting</Term>. `const`, `let`, and `class` hoist their **name** but not their value: the binding exists from the top of the scope but is unreachable until the declaration line runs, which is the TDZ you just met. `var` hoists its name **and** pre-initializes it to `undefined`. Function declarations hoist their entire body, which is why you can call a `function foo() {}` declared at the bottom of a file from the top.

:::note
None of this comes up in day-to-day code. Declare every binding before you reference it and the TDZ never fires. The forms that genuinely surprise, `var` returning `undefined` before its declaration and function declarations called above their definition, only show up in legacy code you're rewriting.
:::

## `Object.freeze` and why the course prefers compile-time typing

`Object.freeze` does what `const` doesn't: it makes an object's top-level properties read-only at runtime. Once frozen, any write to a property throws a `TypeError` in strict mode, which all modules and class bodies use by default. The freeze is **shallow**, like the spread copies from the first lesson, so nested objects stay mutable.

```ts
const config = Object.freeze({ feature: true, env: { tier: 'pro' } });

// config.feature = false; // TypeError in strict mode — top-level write rejected.
config.env.tier = 'free'; // allowed — the freeze is shallow.
```

This course names `Object.freeze` so you recognize it in the wild, then reaches for TypeScript instead. The `readonly` modifier and `as const`, both covered in Chapter 4, "Typing values you know," give the same "this can't be reassigned" guarantee at compile time, with zero runtime cost: the bug becomes a red squiggle in your editor before you run the code, instead of a `TypeError` in production. `Object.freeze` is the right tool only when a runtime guarantee is genuinely required, usually a module exporting a config object that third-party code could tamper with. Inside a SaaS app where you own both ends of every call, that case is almost never, so reach for the typing tools.

## `const` doesn't narrow types

`const` on a primitive narrows the inferred type to the literal value; `const` on an object does not narrow its properties. That asymmetry catches everyone the first time, and the fix is the `as const` you just saw named.


    </CodeTooltips>

    </div>
    On a primitive, `const` makes TypeScript infer the **literal type** `'hello'`, not the wider `string`. Because `const` blocks reassignment and a primitive can't be mutated, the value can only ever be `'hello'`.
  </CodeVariant>

  <CodeVariant label="Object — widens to the property type">
    <div data-mark-color="orange">

    <CodeTooltips tooltips={{
      'feature: true': 'Inferred as `boolean`, not the literal `true`: the object is mutable, so the property could be reassigned and TypeScript widens.',
    }}>

    ```ts
    const config = { feature: true };
    ```

    </CodeTooltips>

    </div>
    On an object, `const` does **not** carry the narrowing through to the properties. TypeScript infers `config.feature` as `boolean`, not `true`, because the object is mutable: nothing stops `config.feature = false` later, as you just saw. So the type checker widens.
  </CodeVariant>
</CodeVariants>

When you want the literal types, the fix is `as const`, which you'll meet in Chapter 4. A preview so you recognize the shape:

```ts
const config = { feature: true } as const;
// inferred type: { readonly feature: true }
```

Two things change: every property becomes `readonly` (the compile-time `Object.freeze`), and every primitive value narrows to its literal type. What matters here is the trigger: write `as const` on an object literal when you want TypeScript to lock the property types, not just the binding.

The two third-bucket cases are both `const`. A `for...of` loop variable feels like it's changing, and the value does change each iteration, but the language creates a fresh binding scoped to the loop body on every pass, so the name is never reassigned; write `let` there and Biome's `useConst` rule flags the reassignment that doesn't exist. An array built with `.push` mutates the array in place, but the binding keeps pointing at the same array. Reach for `let` only when you'd genuinely write `binding = somethingElse` somewhere in the body.
