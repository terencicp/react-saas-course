Picture a teammate who ships `const config = { feature: true }` at the top of a module and considers the value protected. Another module imports `config`, sets `config.feature = false` mid-request to short-circuit a code path, and the user-facing flag flips silently for that whole request. `const` never promised to freeze the value; it only promised that the *name* would keep pointing at the same object.

Now picture a binding declared `let` "just in case" six months ago, never reassigned since, that an unrelated change finally reassigns. Half the rendering pipeline downstream had read the original value once and assumed it would not move. Both bugs share one root: a misunderstanding of what `const` promises, and a habit of reaching for `let` when nothing needs it.

## `const` blocks reassignment, not mutation

`const` is a <Term definition="A name that points to a value. In `const x = 1`, `x` is the binding; `1` is the value.">binding</Term> that cannot be **reassigned**. It says nothing about whether the value the binding points at can be mutated. `const` makes only the first promise.

<BindingDiagram />

`const` locks the arrow in that diagram: you can't repoint it at a different value. It has no opinion about the box on the other end. If that value is mutable, and every object, array, `Map`, `Set`, and class instance is, any code holding a reference can reach in and change its contents. The arrow stays put; the box changes underneath.

```ts
const config = { feature: true };
config.feature = false;
// config = { feature: false };
```

The second line works: it reaches through the existing arrow and changes a property on the object, which `const` doesn't govern. The third line, uncommented, throws `TypeError: Assignment to constant variable.` — it repoints the arrow at a *different* object, and reassignment is what `const` blocks.

For a primitive the distinction collapses, because there is no inside to mutate: you can't change the contents of `42` or `'hello'`. So `const x = 42` behaves as if the value were frozen, simply because the value can't change either way. This is where the bugs come from: the mental model that fits `const PORT = 3000` quietly fails on `const config = { feature: true }`.

The defense isn't `Object.freeze` (covered later in this lesson). It's the copy-then-modify habit from the chapter's first lesson, spread or `structuredClone`, backed by TypeScript's compile-time guards.

## `const` by default, `let` when the binding must change

Write `const` for every binding, and reach for `let` only when the binding itself has to point at something different later. The trigger is not that the value might change; that's the object, and `const` says nothing about it. The trigger is reassignment.

In practice, `let` earns its place in a small set of cases:

- An **accumulator** in a manual loop, such as a `let total = 0;` you increment as you walk a list. The binding reassigns on every iteration, which is the whole point of the loop.
- A **value assigned in a branch** too involved for a ternary: `let role; if (...) { role = 'admin'; } else if (...) { role = 'editor'; } else { role = 'viewer'; }`. This is usually a sign the branches should move into a helper that returns the value, after which the call site is `const role = pickRole(...)` again.
- A **loop counter** in a classic `for (let i = 0; ...; i++)`, when the index is genuinely what you need rather than the element.

Outside those shapes, a `let` you never reassign should be a `const`. Biome's `useConst` rule catches the pattern at build time and names the exact `let` to convert, but build the reading habit anyway: when you see a `let`, ask where it gets reassigned.

## Block scope and the Temporal Dead Zone

Two mechanical rules sit underneath `const` and `let`, and they're tightly linked. The first is **block scope**: every `const` and `let` binding is scoped to the nearest pair of curly braces enclosing it, whether that's a function body, an `if` branch, a `for` loop, an arrow-function body, or a bare `{ ... }` block. The scope is **lexical**, determined by where the binding is written, not by the call stack that reaches it at runtime.

```ts
if (user.isAdmin) {
  const tier = 'pro';
  console.log(tier);
}

// console.log(tier); // ReferenceError — tier is not visible out here
```

The binding lives inside its block and nowhere else. `var` is the exception: because it is function-scoped, a `var` declared inside an `if` block leaks out to the surrounding function, the leak block scope was designed to eliminate.

The second rule stops a different bug class. Every `const` and `let` binding enters a state called the <Term definition="The period between entering a scope and reaching a let/const declaration. The binding exists (the parser saw it) but accessing it throws a ReferenceError.">Temporal Dead Zone</Term> (TDZ) the moment its scope starts, and stays there until the line that declares it runs. Access the binding while it's in the TDZ and you get a `ReferenceError`, not a value.

This closes an old `var` hazard. With `var`, accessing the binding before its declaration line silently returned `undefined`, because the engine pre-initialized the name to `undefined` before any code ran. A typo or a wrongly ordered statement gave you `undefined` at runtime instead of an error, and that `undefined` propagated until it surfaced somewhere unrelated. The TDZ makes the same access fail at the moment the bad code runs, the cheapest moment to fix it.

The fix isn't to swap to `var`; it's to declare the binding before you use it. That points to a habit worth building now: **declare bindings at the top of the scope where they're used**. Then anyone scanning a function top-down sees every declaration before its first use, and the TDZ never fires.

All of this is <Term definition="The compile-time process where the engine collects every name in a scope and pre-registers it before any code runs. For `var`, the name is initialized to `undefined`; for `let`, `const`, and `class`, the name is registered but unreachable until the declaration line (the TDZ).">hoisting</Term>. `const`, `let`, and `class` hoist their **name** but not their value: the binding exists from the top of the scope but is unreachable until its declaration line, which is the TDZ. `var` hoists its name **and** pre-initializes it to `undefined`. Function declarations hoist their entire body, so you can call a `function foo() {}` declared at the bottom of a file from the top.

:::note
The `var` and function-declaration behaviors aren't on this course's path; you'll only meet them in legacy code you're rewriting. Declare every binding before you reference it and hoisting stays invisible.
:::

## `Object.freeze` and why the course prefers compile-time `readonly`

`Object.freeze` is the standard-library tool that does what `const` doesn't: it makes an object's top-level properties read-only **at runtime**. Writing to a frozen property throws a `TypeError` in strict mode, which every module and class body uses by default. The freeze is **shallow**, like the spread copies from the first lesson, so nested objects stay mutable.

```ts
const config = Object.freeze({ feature: true, env: { tier: 'pro' } });

// config.feature = false; // TypeError in strict mode — top-level write rejected.
config.env.tier = 'free'; // allowed — the freeze is shallow.
```

The course names `Object.freeze` so you recognize it, then reaches for TypeScript instead. The `readonly` modifier and `as const`, covered in Chapter 4, give the same "can't be reassigned" guarantee at **compile time** with zero runtime cost: the bug becomes a red squiggle in your editor before you ever run the code, instead of a `TypeError` in production. `Object.freeze` is the right tool only when a runtime guarantee is genuinely required, usually a module exporting a config object that third-party code could tamper with. Inside an app where you control both ends of every call, reach for the typing tools.

## `const` doesn't narrow types

One more value-model fact before the exercise. `const` on a primitive narrows the inferred type to the literal value; `const` on an object widens it. That asymmetry catches everyone the first time, and the fix is `as const`.

The type checker widens to reflect that.
  </CodeVariant>

When you want the literal types, reach for `as const`:

```ts
const config = { feature: true } as const;
// inferred type: { readonly feature: true }
```

Two things change: every property becomes `readonly` (the compile-time `Object.freeze`), and every primitive value narrows to its literal type. So the trigger to remember: when you write `const` on an object literal and want the property types locked as well as the binding, `as const` is the tool. Chapter 4, "Typing values you know," covers how the inference works.

Sort these eight bindings into three buckets. The first two are straightforward; the third is for cases where the value *looks* like it changes but the binding doesn't, so `const` is the only correct call even though a quick reading reaches for `let`. The skill is recognizing those cases as `const` on sight.

A `for...of` loop variable feels like it changes, and the *value* does change each pass, but the language creates a fresh binding scoped to the loop body each iteration, so the name is never reassigned. Write `let` there and you're claiming a reassignment that doesn't exist; Biome's `useConst` rule flags it. An array built with `.push` mutates in place, but the binding still points at the same array, so it never reassigns either. Both are `const`. Reach for `let` only when you'd genuinely write `binding = somethingElse` somewhere in the body.
