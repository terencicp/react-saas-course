Open a browser console and type `0.1 + 0.2`. You'll get `0.30000000000000004`. That trailing noise causes billing bugs: an invoice total that drifts by a cent after summing twelve line items, a `$1.005` discount that rounds down instead of up. Every JavaScript `number` is a 64-bit floating-point value, and most decimal fractions can't be stored exactly in binary, so decimal arithmetic comes back slightly off.

Two practices close this bug class. Store money as integer cents, never dollars (1995, not 19.95), and validate numbers at the boundary so malformed values never reach a database.

## Why `0.1 + 0.2` doesn't equal `0.3`

console.log(0.1 + 0.2);

The engine stores each as its closest 64-bit binary fraction, and adding the two approximations lands on a value that prints as `0.30000000000000004`.

The rule that matters: **fractional arithmetic in `number` is approximate, integer arithmetic is exact**.

This same standard is why `NaN === NaN` was `false` last lesson: IEEE 754 marks an invalid calculation as `NaN` and makes it unequal even to itself.

## The integer-cents rule

Store money as the integer count of the currency's smallest unit, the minor unit defined by <Term definition="ISO 4217 codes each currency and its number of minor-unit decimals: USD has 2 (cents), JPY has 0, BHD has 3 (fils). That count sets how many integer units make one major unit.">ISO 4217</Term>: cents for USD, pence for GBP. Convert between the integer and a human-readable string only at the boundaries, when accepting form input and when rendering for display. Never store, sum, multiply, or compare dollars-as-floats in between.

This isn't a course preference; real systems require it. Stripe's API takes `amount` as an integer in the currency's minor units (`1000` to charge ten dollars, `10` to charge ten yen), other payment processors do the same, and your database stores money the same way.

The round-trip: a string comes in, an integer sits in storage, a string goes back out.

```ts
const userInput = '19.95';
const dollars = Number(userInput);                  // 19.95
const cents = Math.round(dollars * 100);            // 1995

// store `cents` as an integer; pass `cents` to Stripe; sum cents in SQL.

const displayDollars = (cents / 100).toFixed(2);    // '19.95'
const displayString = `$${displayDollars}`;         // '$19.95'
```

`Number(userInput)` parses the string into the same inexact float we just warned about. `Math.round(dollars * 100)` then fixes it: the multiplication moves the value into the cents domain, where it may land on `1995.0000000000002`, and the rounding erases that noise to leave the exact integer `1995`. From there it sums, multiplies, and compares exactly. To display, divide by 100 and let `toFixed(2)` format the result.

:::caution
Use `Math.round` for money, not `Math.floor` or `Math.trunc`. `Math.floor` always rounds down and `Math.trunc` chops toward zero, either of which can drop a cent when the floating-point noise lands just below the integer.
:::

For display, `Intl.NumberFormat` produces locale-aware symbols, grouping, and minor-unit decimals automatically (`$1,234.56` in `en-US`, `1 234,56 €` in `fr-FR`).

## Boundary checks with the `Number.is*` family

The integer-cents rule is only as good as the values you store. A string from a form, a JSON payload from another service, a number from a calculation: each must be confirmed as a finite integer before it lands in the database. The `Number` namespace ships three <Term definition="A function that returns a boolean, used to test whether a value satisfies some condition.">predicates</Term> for exactly those boundary checks.

```ts
Number.isFinite(parsed);       // not NaN, not ±Infinity
Number.isInteger(parsed);      // a whole number, no fractional part
Number.isSafeInteger(parsed);  // a whole number under 2^53
```

**`Number.isFinite(x)`** is the first check at any boundary that produces a number. It returns `false` for `NaN`, `Infinity`, and `-Infinity`, the three values that otherwise propagate silently and surface days later as `$NaN` on an invoice. Make it a habit: follow every `Number(input)` with a `Number.isFinite` guard.

**`Number.isInteger(x)`** confirms a whole number with no fractional part, returning `false` for `NaN` and the infinities too. Reach for it when a value should *already* be an integer by the time you receive it: a cents amount read back from another service, a row count, a quantity field on a payload. The function below doesn't use it, because `Math.round` produces the integer there.

**`Number.isSafeInteger(x)`** returns `false` past `Number.MAX_SAFE_INTEGER` (`2^53 − 1`), beyond which a `number` can no longer represent integers exactly. Cents up to about $90 trillion fit under this ceiling, so in practice it guards values arriving from 64-bit external systems. A failure here is the signal to reach for `BigInt`, covered next.

One trap before you make `Number()` your boundary parser:

```ts
console.log(Number(''));      // 0
console.log(Number('   '));   // 0
```

Both return `0`, not `NaN`, so `Number.isFinite(Number(''))` is `true`: an empty form field passes validation as a valid zero and lands as a silent $0.00 charge. To reject empty input, and you almost always should, check the trimmed string before converting:

```ts
const parseCentsInput = (input: string): number => {
  if (input.trim() === '') throw new Error('Empty input');
  const dollars = Number(input);
  if (!Number.isFinite(dollars)) throw new Error('Not a number');
  const cents = Math.round(dollars * 100);
  if (!Number.isSafeInteger(cents)) throw new Error('Amount too large');
  return cents;
};
```

The empty-string guard catches the `Number('') === 0` trap, `Number.isFinite` catches `NaN` and `Infinity` from malformed input, `Math.round` produces integer cents (erasing the multiplication's floating-point noise), and `Number.isSafeInteger` guards the upper bound. Four checks at one boundary, and nothing bad leaks downstream.

`Number.isNaN` from the previous lesson tests only for `NaN`; at a boundary prefer `Number.isFinite`, which rules out `NaN` and both infinities in one call.

## When to use `BigInt`

Money does not need it. Integer cents stay under 2^53 for any single transaction up to about $90 trillion, far beyond what Stripe accepts in one charge (it caps `amount` at 8 digits, around $1M). Regular `number` covers money.

Three situations do call for it:

- **64-bit external IDs.** Twitter Snowflake IDs and some database `BIGINT` columns exceed `Number.MAX_SAFE_INTEGER`, so parsing one as a `number` silently rounds away its low bits and can collapse two distinct IDs into one. Read them as `BigInt`, or as a string if you never do arithmetic on them.
- **Counters that cross 2^53.** Nanosecond timestamps over multi-decade ranges, or cumulative counters in high-volume telemetry.
- **Crypto and hash arithmetic.** Modular exponentiation, large-prime work, and hash construction, where the values are deliberately huge and overflow is silently disastrous.

Write a `BigInt` as a numeric literal with an `n` suffix:

```ts
const snowflake = 1234567890123456789n;   // `n` suffix is the BigInt literal
const next = snowflake + 1n;              // BigInt arithmetic — works
// const broken = snowflake + 1;          // TypeError: cannot mix BigInt and number
```

:::caution
`BigInt` brings friction the moment you reach for it:

- **It does not mix with `number`.** `1n + 1` throws `TypeError`; convert explicitly with `Number(bigint)` (lossy for large values) or `BigInt(number)`.
- **`Math.*` rejects it.** The whole namespace works on `number` only.
- **`JSON.stringify` throws on it.** Sending it over the wire needs a custom replacer, usually converting to a string.
- **TypeScript's `bigint` type is distinct from `number`,** so the compiler enforces the no-mixing rule before you ship.
:::

So the rule is: **use `number` until a real overflow forces the switch.**

## Converting strings to numbers

Every entry point that reads a string as a number (form input, query parameter, JSON field, environment variable) gets the same shape: `Number(input)` to parse, then `Number.isFinite(result)` to validate, plus the empty-string guard from above. That is the default; the other three conversions each fit a narrow case. Compare them on a clean `'19.95'` and a `'12px'` with trailing garbage:

<CodeVariants>
  <CodeVariant label="Number(input)">

    ```ts {1,2}
    Number('19.95');   // 19.95
    Number('12px');    // NaN
    ```

    </div>
    **The default.** Strict: it returns `NaN` unless the whole string is a number. Pair it with `Number.isFinite` and the empty-string guard for a complete boundary check. Reach for it unless another form has a specific trigger.
  </CodeVariant>

  <CodeVariant label="parseInt(input, 10)">
    <div data-mark-color="orange">

    ```ts {1,2}
    parseInt('19.95', 10);   // 19 — lossy on fractions!
    parseInt('12px', 10);    // 12
    ```

    </div>
    **The dimension-string reach.** Reads the leading digits and ignores trailing garbage, right for CSS strings like `'12px'` or `'200rem'`. For user input it's almost always wrong: it silently drops the fraction of `19.95`. Pass the <Term definition="The number base a string of digits is read in: 10 for decimal, 16 for hexadecimal. parseInt's second argument; pass it explicitly so the base is never inferred.">radix</Term> `10` so the base is never in question.
  </CodeVariant>

  <CodeVariant label="parseFloat(input)">
    <div data-mark-color="orange">

    ```ts {1,2}
    parseFloat('19.95');   // 19.95
    parseFloat('12px');    // 12
    ```

    </div>
    **Rarely the right answer.** Forgiving like `parseInt`, but returns a float. Its cases are narrow enough that `Number()` with validation reads more clearly.
  </CodeVariant>

  <CodeVariant label="+input">
    <div data-mark-color="blue">

    ```ts {1,2}
    +'19.95';   // 19.95
    +'12px';    // NaN
    ```

    </div>
    **The shortcut.** Unary plus runs the same conversion as `Number(input)`. Legible in a one-line callback, but `Number(input)` reads better in shared code, the form this course uses.
  </CodeVariant>
</CodeVariants>

The function matters because `NaN` propagates: every arithmetic operation involving it yields `NaN`, so one bad input spreads silently downstream and surfaces later as `$NaN` on an invoice. The boundary check above stops it at the entry point, so no arithmetic call site needs a defensive branch.

`Number.parseInt` and `Number.parseFloat` are namespaced aliases with identical behavior.

## Practice: write `dollarsToCents`

Implement `dollarsToCents(input)` yourself. The tests below cover each trap.

<ScriptCoding
  instructions="Implement dollarsToCents(input) using input.trim() to check for emptiness, Number() to parse, Number.isFinite to reject NaN/Infinity, Math.round to land on integer cents, and Number.isSafeInteger to guard the upper bound. Throw 'Invalid amount' for non-numeric or empty inputs; throw 'Amount too large' for values past Number.MAX_SAFE_INTEGER."
  starter={`function dollarsToCents(input) {
  // 1. Reject empty/whitespace input by throwing 'Invalid amount'.
  // 2. Parse the input string into a number using Number().
  // 3. Reject NaN and Infinity by throwing 'Invalid amount'.
  // 4. Multiply by 100 and round to the nearest integer.
  // 5. Reject unsafe integers by throwing 'Amount too large'.
  // 6. Return the integer cents.
}`}
  tests={`
test('converts a typical dollar amount', () => {
  expect(dollarsToCents('19.95')).toBe(1995);
});
test('handles whole dollars', () => {
  expect(dollarsToCents('20')).toBe(2000);
});
test('handles zero', () => {
  expect(dollarsToCents('0')).toBe(0);
});
test('rounds away floating-point noise', () => {
  // 19.95 * 100 in floats is 1995.0000000000002 — Math.round saves us.
  expect(dollarsToCents('19.95')).toBe(1995);
});
test('throws on non-numeric input', () => {
  expect(() => dollarsToCents('twenty')).toThrow('Invalid amount');
});
test('throws on empty input', () => {
  // Number('') === 0 — without an explicit empty-string guard, this would
  // silently return 0 and the user gets a $0.00 charge in their database.
  expect(() => dollarsToCents('')).toThrow('Invalid amount');
});
test('throws on whitespace input', () => {
  // Number('   ') === 0 too. Same footgun.
  expect(() => dollarsToCents('   ')).toThrow('Invalid amount');
});
test('throws on Infinity', () => {
  expect(() => dollarsToCents('Infinity')).toThrow('Invalid amount');
});
`}
/>

The empty-string and whitespace tests are the load-bearing ones: `Number('')` is `0`, so `input.trim() === ''` plus `Number.isFinite` is the guard that catches what `!isNaN(Number(input))` lets through. Reuse this shape at every numeric boundary.
