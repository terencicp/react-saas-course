Open a browser console and type `0.1 + 0.2`. You'll get `0.30000000000000004`. That tiny tail of digits causes real billing bugs: an invoice total that drifts by a cent after summing twelve line items, or a `$1.005` discount that rounds down to `$1.00` when it should have rounded up. Every JavaScript `number` is a 64-bit floating-point value, and most decimal fractions can't be stored exactly in binary, so most decimal arithmetic comes back slightly off. Two rules fix this. First, a structural one: store money as integer cents, never dollars. Second, a boundary one: validate numbers before they reach the database, so malformed values never land in a column.

## Why `0.1 + 0.2` doesn't equal `0.3`

Predict what these three lines print. The first two show the classic surprise; the third points to the fix.

<PredictOutput expected={`0.30000000000000004
0.30000000000000004
19.95`}>

```ts
console.log(0.1 + 0.2);
console.log(0.1 * 3);
console.log(1995 / 100);
```

<PredictWhy>

Every JavaScript `number` is a 64-bit double-precision float per the <Term definition="The IEEE 754 standard defines binary floating-point representation. JavaScript's `number` type is the 64-bit double-precision variant — 53 bits of mantissa, 11 bits of exponent. Most decimal fractions can't be represented exactly in binary.">IEEE 754</Term> standard. That representation is **exact** for integers up to ±2^53−1, but only **approximate** for fractions whose binary expansion never terminates, which is most decimal fractions, `0.1` and `0.2` among them. So inside the engine each is stored as the closest 64-bit binary fraction, not its exact decimal value, and adding those two approximations gives a value whose closest decimal printout is `0.30000000000000004`.

The third line is the opposite case. `1995 / 100` prints exactly `19.95` because `1995` is an integer, exact in binary, and dividing it produces a value the engine can print without that trailing noise. Integers stay exact while fractions drift.

</PredictWhy>

</PredictOutput>

You don't need to memorize the mantissa bit count or the rounding modes. What matters is the consequence: **fractional arithmetic in `number` is approximate, integer arithmetic is exact**. Every decision about handling money in this stack follows from that fact.

This same standard is why `NaN === NaN` was `false` in the previous lesson. IEEE 754 uses `NaN` to mark a calculation as invalid, and making it unequal even to itself guarantees no accidental equality check mistakes it for a valid value.

## The integer-cents rule

Here's the rule that closes the bug class: **store money as the integer count of the smallest unit of the currency.** That means cents for USD, pence for GBP, and the appropriate minor unit per <Term definition="The ISO 4217 standard codes every currency and its minor unit. USD has 2 minor-unit decimals (cents); JPY has 0; BHD has 3 (fils). The minor-unit count sets how many integer units make up one major unit of the currency.">ISO 4217</Term> for whatever currency you're handling. Convert between that integer and a human-readable string only at the boundaries: when accepting input from a form, and when rendering for display. Never store, sum, multiply, or compare dollars-as-floats in between.

This is the rule the production stack you're about to build on already enforces. Stripe's API takes `amount` as an integer in the currency's minor units (`1000` to charge ten dollars, `10` to charge ten yen), as does every modern payment processor. Unit 5 applies it again at the database boundary: money lives in an integer cents column, a Postgres `bigint` mapped through Drizzle, rather than a `numeric` dollars column, so a value can round-trip from JS to Postgres and back without ever passing through a float. The wire format, the database, and the payment processor all agree on integers, and this lesson teaches you to write the application code that respects that agreement.

A string comes in from the user, an integer sits in storage, and a string goes back out for display:

```ts
const userInput = '19.95';
const dollars = Number(userInput);                  // 19.95
const cents = Math.round(dollars * 100);            // 1995

// store `cents` as an integer; pass `cents` to Stripe; sum cents in SQL.

const displayDollars = (cents / 100).toFixed(2);    // '19.95'
const displayString = `$${displayDollars}`;         // '$19.95'
```

`Number(userInput)` parses the string into a float, and yes, that float is the same inexact `19.95` we just warned about; the next line fixes it. `Math.round(dollars * 100)` does two jobs at once. The multiplication moves the value into the cents domain, where floating-point noise may leave it on something like `1995.0000000000002`, and the rounding erases that noise to recover the exact integer `1995`. From here the value is an integer, so it sums, multiplies, and compares exactly. On the way out, dividing by 100 recovers the dollar value and `toFixed(2)` formats it for display. Storage is an integer; the boundaries are strings.

:::caution
`Math.round` is not the same as `Math.floor` or `Math.trunc`. `Math.round` rounds to the nearest integer, `Math.floor` always rounds down, and `Math.trunc` chops off the fractional part. Use `Math.round` for money. `Math.floor` would lose a cent whenever floating-point noise lands just below the integer, and `Math.trunc` does the same toward zero. Some multi-currency accounting systems are legally required to use banker's rounding (round half to even); for those, reach for a decimal library. That's out of scope here, and the cent boundary handles the large majority of SaaS use cases.
:::

For formatting currency for human display, the right tool is `Intl.NumberFormat`, which handles locale-aware symbols, grouping, and minor-unit decimals automatically (`$1,234.56` in `en-US`, `1 234,56 €` in `fr-FR`). The `toFixed(2)` shape above is fine for getting your first product to launch; you'll move to `Intl.NumberFormat` when display localization lands in a later unit. Either way, the storage rule doesn't change.

## The `Number.is*` boundary guards

The integer-cents rule is only as good as the values you actually store. A string from a form, a JSON payload from another service, a number coerced from a calculation: each one needs to be confirmed as a finite integer before it lands in the database. JavaScript ships three predicates on the `Number` namespace that give you exactly that boundary check.

```ts
Number.isFinite(parsed);       // not NaN, not ±Infinity
Number.isInteger(parsed);      // a whole number, no fractional part
Number.isSafeInteger(parsed);  // a whole number under 2^53
```

**`Number.isFinite(x)`** is the first check at any boundary that produces a number. It returns `false` for `NaN`, `Infinity`, and `-Infinity`, the three values that would otherwise propagate silently through downstream calculations and surface days later as `$NaN` on an invoice. Make it a habit: follow every `Number(input)` with a `Number.isFinite` guard.

**`Number.isInteger(x)`** confirms the value is a whole number with no fractional part. Reach for it when a value should *already* be an integer by the time you receive it (a cents amount read back from another service, a row count from a query, a quantity field on a JSON payload) and you want to verify that before trusting it. It also returns `false` for `NaN` and the infinities, so it works on its own as an integer guard. You won't see it inside the conversion function below, because there `Math.round` produces the integer, so a follow-up `isInteger` check would be redundant.

**`Number.isSafeInteger(x)`** checks the value against the boundary past which a regular `number` can no longer represent integers exactly. It returns `false` for integers larger than `Number.MAX_SAFE_INTEGER` (which is `2^53 − 1`, or `9_007_199_254_740_991`). Money in cents up to about $90 trillion fits comfortably under this ceiling, so in practice this check guards values coming in from 64-bit external systems. When a value fails it, that's the signal to reach for `BigInt`, covered in the next section.

One footgun in `Number()` is worth calling out before you use it as the boundary parser everywhere:

```ts
console.log(Number(''));      // 0
console.log(Number('   '));   // 0
```

`Number('')` and `Number('   ')` both return `0`, not `NaN`. That means `Number.isFinite(Number(''))` is `true`, so an empty form field sails through your validation as a valid zero dollars. The result is a silent $0.00 charge in the database. If empty input should be rejected, and it almost always should, check the trimmed string before converting:

```ts
const parseCentsInput = (input: string): number => {
  if (input.trim() === '') throw new Error('Empty input');
  const dollars = Number(input);
  if (!Number.isFinite(dollars)) throw new Error('Not a number');
  const cents = Math.round(dollars * 100);
  if (!Number.isSafeInteger(cents)) throw new Error('Amount too large');
  return cents;
};
```

Each line guards one failure. The empty-string check catches the `Number('') === 0` footgun. `Number.isFinite` catches `NaN` and `Infinity` from malformed input. `Math.round` converts to integer cents and erases the multiplication's floating-point noise. And `Number.isSafeInteger` guards the upper bound, past which values would lose precision in any later arithmetic. Four lines of validation at a single boundary, and nothing bad leaks downstream. In a later unit you'll meet Zod, which folds this exact shape into a declarative schema (`z.string().min(1).pipe(z.coerce.number().int().finite())`). The runtime checks survive and the boilerplate disappears, but the boundary discipline stays the same.

A related note: `Number.isNaN` (from the previous lesson) answers the question "is this exactly the `NaN` value?". At boundaries, though, `Number.isFinite` is usually what you actually mean, because it covers `NaN` and the two infinities in one call.

## When to reach for `BigInt`

Start with what does *not* trigger `BigInt`: money. Integer cents under 2^53 cover any single transaction up to about $90 trillion, far past the 8-digit cap (around $1M USD) Stripe puts on an individual `amount`, and past any balance a SaaS will plausibly hold. Regular `number` already covers money.

`BigInt` is the right reach in three situations:

- **64-bit external IDs.** Twitter Snowflake IDs and some database `BIGINT` columns exceed `Number.MAX_SAFE_INTEGER`, so parsing them as a regular `number` corrupts them silently: the lowest bits round away, and two distinct IDs can collapse to one value. Read them as `BigInt`, or as a string if you never do arithmetic on them.
- **Counters that genuinely cross 2^53.** Rare in SaaS, but it happens: nanosecond timestamps over multi-decade ranges, cumulative event counters in high-volume telemetry.
- **Crypto and hash arithmetic.** Modular exponentiation, large-prime work, hash construction: places where the values are deliberately huge and overflow is silently disastrous.

You write a `BigInt` as a numeric literal with an `n` suffix:

```ts
const snowflake = 1234567890123456789n;   // `n` suffix is the BigInt literal
const next = snowflake + 1n;              // BigInt arithmetic — works
// const broken = snowflake + 1;          // TypeError: cannot mix BigInt and number
```

:::caution
`BigInt` carries real friction the moment you reach for it:

- **It does not mix with `number` in expressions.** `1n + 1` throws `TypeError`, and TypeScript's distinct `bigint` type catches the same mistake at compile time. Converting is explicit: `Number(bigint)` (lossy for large values) and `BigInt(number)`.
- **`Math.*` does not accept `BigInt`.** `Math.round`, `Math.sqrt`, and the rest of the namespace work on `number` only.
- **`JSON.stringify` throws on `BigInt`.** Serializing it needs a custom replacer, typically converting to a string.
:::

Because that cost is real, use `number` until a genuine overflow forces the switch.

## Converting strings to numbers

Every entry point that takes a string and treats it as a number (form input, query parameter, JSON field, environment variable) gets the same shape: `Number(input)` to parse, then `Number.isFinite(result)` to validate, plus the empty-string guard from the section above.

JavaScript ships four ways to turn a string into a number, and only one is the default. Run each against the same two inputs, a clean `'19.95'` and a `'12px'` with trailing garbage, and the differences become clear:

<CodeVariants>
  <CodeVariant label="Number(input)">
    <div data-mark-color="green">

    ```ts {1,2}
    Number('19.95');   // 19.95
    Number('12px');    // NaN
    ```

    </div>
    **The default.** It returns `NaN` unless the whole string is a number. Pair it with `Number.isFinite` and the empty-string guard, and the boundary check is done. Reach for this unless one of the other three has a specific trigger.
  </CodeVariant>

  <CodeVariant label="parseInt(input, 10)">
    <div data-mark-color="orange">

    ```ts {1,2}
    parseInt('19.95', 10);   // 19 — lossy on fractions!
    parseInt('12px', 10);    // 12
    ```

    </div>
    **The dimension-string reach.** It reads the leading digits and ignores trailing garbage, exactly right for CSS strings like `'12px'` or `'200rem'`, and almost always wrong for user input, because it silently drops the fractional part of `19.95`. The radix argument is required so old engines don't read a leading zero as base 8.
  </CodeVariant>

  <CodeVariant label="parseFloat(input)">
    <div data-mark-color="orange">

    ```ts {1,2}
    parseFloat('19.95');   // 19.95
    parseFloat('12px');    // 12
    ```

    </div>
    **Rarely the right answer.** Same forgiving "ignore trailing garbage" behavior as `parseInt`, but it returns a float. Its use cases are narrow enough that `Number()` with validation reads more clearly at the call site every time.
  </CodeVariant>

  <CodeVariant label="+input">
    <div data-mark-color="blue">

    ```ts {1,2}
    +'19.95';   // 19.95
    +'12px';    // NaN
    ```

    </div>
    **The shortcut.** Unary plus triggers the same conversion as `Number(input)`, so the behavior is identical. It reads fine in a one-line callback, but `Number(input)` is clearer in shared code, and that's the form this course writes.
  </CodeVariant>
</CodeVariants>

This matters beyond picking the right function, because `NaN` propagates. Every arithmetic operation involving `NaN` yields `NaN`: `NaN + 1`, `NaN * 2`, and `Math.round(NaN)` are all `NaN`. A single bad input quietly spreads through every later calculation and surfaces as `$NaN` on an invoice, or as a `null` in a database column where a serializer choked on the way. The fix is the boundary check (`Number.isFinite` right after `Number()`, with the empty-string guard upstream), not a defensive branch at every arithmetic call site. Catch the bad value where it enters, and the rest of your code never has to handle it.

`Number.parseInt` and `Number.parseFloat` exist as namespaced aliases with identical behavior; neither form is preferred over the global.

## Practice: implement `dollarsToCents`

Implement `dollarsToCents(input)` so it converts a dollar string into an integer cents value and rejects every shape of invalid input with a clear error. The failing tests will point you at the footguns.

<ScriptCoding
  instructions="Implement dollarsToCents(input). Use input.trim() to reject empty or whitespace input, Number() to parse, Number.isFinite to reject NaN and Infinity, Math.round to land on integer cents, and Number.isSafeInteger to guard the upper bound. Throw 'Invalid amount' for empty or non-numeric input; throw 'Amount too large' for values past Number.MAX_SAFE_INTEGER."
  starter={`function dollarsToCents(input) {
  // 1. Reject empty/whitespace input by throwing 'Invalid amount'.
  // 2. Parse the input string into a number using Number().
  // 3. Reject NaN and Infinity by throwing 'Invalid amount'.
  // 4. Multiply by 100 and round to the nearest integer.
  // 5. Reject unsafe integers by throwing 'Amount too large'.
  // 6. Return the integer cents.
}`}
  tests={`
test('converts a typical dollar amount', () => {
  expect(dollarsToCents('19.95')).toBe(1995);
});
test('handles whole dollars', () => {
  expect(dollarsToCents('20')).toBe(2000);
});
test('handles zero', () => {
  expect(dollarsToCents('0')).toBe(0);
});
test('rounds away floating-point noise', () => {
  // 19.95 * 100 in floats is 1995.0000000000002 — Math.round saves us.
  expect(dollarsToCents('19.95')).toBe(1995);
});
test('throws on non-numeric input', () => {
  expect(() => dollarsToCents('twenty')).toThrow('Invalid amount');
});
test('throws on empty input', () => {
  // Number('') === 0 — without an explicit empty-string guard, this would
  // silently return 0 and the user gets a $0.00 charge in their database.
  expect(() => dollarsToCents('')).toThrow('Invalid amount');
});
test('throws on whitespace input', () => {
  // Number('   ') === 0 too. Same footgun.
  expect(() => dollarsToCents('   ')).toThrow('Invalid amount');
});
test('throws on Infinity', () => {
  expect(() => dollarsToCents('Infinity')).toThrow('Invalid amount');
});
`}
/>

The empty-string and whitespace tests are the load-bearing ones. Without the explicit `input.trim() === ''` guard, `Number('')` returns `0`, sails through `Number.isFinite`, rounds to integer `0`, and your function reports a successful zero-cent charge for an empty form submission. That is why the check pairs `input.trim()` with `Number.isFinite` rather than `!isNaN(Number(input))`, which has the same hole. The shape you just wrote repeats at every numeric boundary in the rest of the course.
