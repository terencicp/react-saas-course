Two snippets surprise almost every developer the first time they see them. The first compares two objects with identical contents.

```ts
console.log({ id: 1 } === { id: 1 }); // false
```

The second compares a value to itself.

```ts
console.log(NaN === NaN); // false
```

JavaScript has three equality operators, plus two edge cases the spec calls out. The goal is to reach for one operator by default and recognize the rest on sight: you'll write `===` automatically, know the two cases where its answer can mislead you, and know the rare moments when another operator fits better.

## How `===` compares primitives and objects

`===` asks one question: are these the same value? The answer depends on what kind of value you give it, the same split from the previous lesson. Primitives are values themselves; objects are references to a value that lives elsewhere.

For **primitives**, `===` compares the value itself. `'ada' === 'ada'` is `true` because the two strings *are* the same value: a primitive has no identity separate from its content. `42 === 42`, `true === true`, and `null === null` are all `true` for the same reason.

For **objects**, `===` compares the reference: the arrow, not the contents of the box it points at. Two object literals with identical contents are two separate allocations, so two arrows, so `===` returns `false`. The same object reached through two names is `===` to itself, because both names point at the same box.

```ts
console.log('ada' === 'ada');                       // true
console.log({ id: 1 } === { id: 1 });               // false
const user = { id: 1 };
const alias = user;
console.log(user === alias);                        // true
```

So `===` answers "are these the same value?" for primitives and "are these the same allocation?" for objects. It never answers "do they have the same shape?" The language has no operator for that, and we'll return to it at the end of the lesson.

## Why the course never writes `==`

JavaScript has a second equality operator, `==`, that the course never writes.

`==` runs a table of coercion rules before comparing: strings become numbers, objects become primitives, `null` and `undefined` count as equal to each other but not to `false`, and the special cases pile up from there. Nobody remembers the full table correctly under deadline pressure. The one occasionally defensible use, `x == null` to match both `null` and `undefined`, is unnecessary in this stack: the next chapter introduces the `??` operator and explicit nullish checks, which read better without pulling in the coercion table.

Avoiding `==` takes no discipline, because the tooling enforces it. Biome's `noDoubleEquals` rule, enabled in the canonical `biome.json` you'll set up later in the course, flags every `==` and `!=` at lint time, so a slip becomes a build error instead of something a reviewer has to catch.

:::caution
If you see `==` in legacy code or in code from an AI assistant, change it to `===` and re-test. The behavior will change to the behavior you actually wanted.
:::

`NaN === NaN` is `false` because <Term definition="The floating-point standard JavaScript's `number` type is built on; the source of every floating-point surprise, covered in the next lesson on money math.">IEEE 754</Term> specifies that `NaN` is not equal to anything, including itself. That choice is what makes `NaN` a useful "this calculation was invalid" marker: once a value is `NaN`, no accidental equality check ever matches it back into a valid bucket. The next lesson explains why JavaScript produces `NaN` in the first place; for now the rule is enough: never compare a value to `NaN` with `===`.

`+0 === -0` (and `0 === -0`) is `true` because the spec defines `===` that way. Signed zero exists, and it matters for graphics, scientific computing, and a few hash-key designs, but in everyday SaaS code the distinction never shows up.

Both behaviors are guaranteed by the spec across every JavaScript engine you'll ever target. They aren't bugs and they won't change. They are the small cost of having `===` defined precisely enough to behave the same everywhere.

## `Object.is`: like `===`, but `NaN` and signed zero differ

JavaScript has a third equality form, `Object.is(a, b)`. Despite the name, it has nothing to do with objects. It matches `===` everywhere except the two edge cases above: `Object.is(NaN, NaN)` is `true`, and `Object.is(+0, -0)` is `false`.

```ts
console.log(Object.is(NaN, NaN));     // true   — diverges from ===
console.log(Object.is(+0, -0));       // false  — diverges from ===
console.log(Object.is('ada', 'ada')); // true   — same as ===
console.log(Object.is({}, {}));       // false  — same as ===
```

There are two real-world places where `Object.is` is the right tool:

- **Custom memoization keys** where bit-pattern identity matters, for instance a memoizer that needs to treat `NaN` as a valid input distinct from "no value."
- **React's change detection.** When you set state, React uses `Object.is`, not `===`, to decide whether the value changed and the component needs to re-render. You'll meet this rule again in the React chapters.

So default to `===` everywhere, and reach for `Object.is` only when one of those two cases applies. When you do, add a comment explaining why, or the next reader will assume it's a typo for `===`.

## `Number.isNaN` over the global `isNaN`

Because `NaN === NaN` is `false`, you can't write `if (x === NaN)` to test for `NaN`. You need a dedicated function, and JavaScript provides two. Only one is safe.

The global `isNaN(x)` is the legacy form: it coerces its argument to a number before testing, which is almost never what you want. `isNaN('hello')` is `true`, not because `'hello'` is `NaN`, but because coercing `'hello'` to a number *produces* `NaN`. `isNaN(undefined)` is `true` for the same reason. The function answers a different question than its name suggests.

`Number.isNaN(x)` skips the coercion. It returns `true` only when the value you pass is the actual `NaN`, and `false` for everything else.

The global form gives misleading answers for `'hello'` and `undefined`; the namespaced form reports only whether the value is actually `NaN`. The same holds for `Number.isFinite(x)` over `isFinite(x)`: the global coerces, the namespaced form doesn't. Whenever you check a property of a number, use the `Number.*` functions, since the unprefixed globals are legacy forms that coerce.

## JavaScript has no structural equality

There's one comparison we haven't covered: checking two objects for the same shape and the same values. JavaScript has no built-in operator or function for it. Comparing `{ id: 1, name: 'Ada' }` to another object with identical fields and values requires either a third-party library (`fast-deep-equal`, `lodash.isEqual`) or a hand-written recursive walk, and the early units pull in neither.

Instead, the course teaches patterns that avoid the question. Structural equality rarely needs to be written by hand when your data model is shaped well, and three patterns cover the cases you'll meet in this stack:

- **Compare by primary key.** Two invoice rows are the same invoice when `a.id === b.id`, and only then. Database-shaped data carries its identity in the ID column, so equality at the application layer reduces to comparing two strings.
- **Derive a stable string key from the relevant fields.** When you need to detect changes for caching or deduplication, build a key (`` `${invoiceId}:${status}:${updatedAt}` ``) and compare strings.
- **Use discriminated unions where each variant has its own shape.** The comparisons that matter then run on the discriminant field, not on the whole object. The TypeScript chapter later in this unit covers this pattern.

At the network and database boundaries you'll reach later, with Zod in the Forms unit and Drizzle in the Postgres unit, comparisons are ID-based by construction.

Every equality decision in the rest of the course, from React state updates to Zod validation to Drizzle row comparisons, follows the same rule: use `===` by default, recognize the two edge cases, and reach for the namespaced `Number.*` functions when you're asking about a number's properties.
