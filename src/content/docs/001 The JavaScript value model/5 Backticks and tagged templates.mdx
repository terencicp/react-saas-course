This lesson starts with two strings, each responsible for a production bug. The first opens the door to SQL injection. The second turns a five-line system prompt into a tangle of `+ '\n'` calls no one wants to edit. The two look nothing alike, but they share one habit: each string is assembled by concatenation.

<CodeVariants>
  <CodeVariant label="Concatenated SQL">
    <div data-mark-color="orange">

    ```ts {2}
    const email = req.body.email;
    const query = 'SELECT * FROM users WHERE email = \'' + email + '\'';
    const rows = await db.execute(query);
    ```

    </div>
    If `email` arrives as `x' OR '1'='1`, the query reads every user in the table. Concatenation lets the attacker's text become part of the query.
  </CodeVariant>

  <CodeVariant label="Concatenated multi-line">
    <div data-mark-color="orange">

    ```ts {1-5}
    const prompt =
      'You are an invoicing assistant.\n' +
      'Customer ' + customerName + ' has ' + unpaidCount + ' unpaid invoices.\n' +
      'Their plan is ' + planName + '.\n' +
      'Reply in fewer than 200 words.';
    ```

    </div>
    The source no longer looks like the string it produces. Adding a line means re-threading the `+` and `\n` pieces by hand, and one missing newline collapses the prompt into a single run-on line the model misreads.
  </CodeVariant>
</CodeVariants>

Both bugs trace back to one habit: gluing pieces together with `+`. The fix is to reach for backticks by default, and add a tag when the string is structured. The first tag is `` sql`...` `` from Drizzle, which makes hand-written queries safe by default. The second is `` dedent`...` `` from npm, which fixes the multi-line indentation problem with a single import.

## Backticks as the default

A <Term definition="A string literal authored with backticks. Supports ${expr} interpolation and multi-line content.">template literal</Term> is a string written with backticks instead of quotes, with two additions: `${expression}` interpolation, and newlines that pass through literally. The expression inside `${...}` can be anything that evaluates to a value: a variable, a property access, a function call, a ternary.

Here are four shapes you'll reach for on a typical day:

```ts
const path = `/invoices/${invoiceId}`;
const heading = `${count} active invoices`;
const className = `rounded-md ${variant === 'primary' ? 'bg-blue-600' : 'bg-zinc-200'}`;
const log = `User ${user.id} requested invoice ${invoice.id}`;
```

Any string built from variables uses a template literal. Reaching for `+` to glue a value into a string is a warning sign: it reads less clearly, loses the placeholder structure that makes the intent obvious, and is the first step toward the two bugs the lesson opened with. The course defaults to single quotes for plain strings, but the moment a `${}` or a newline appears, backticks are the answer.

### Multi-line strings and unwanted indentation

Backticks preserve newlines, so they're also the default for anything that spans more than one line: structured log messages, system prompts, fixture text, email bodies. The catch is that they preserve every character between them, including whitespace the author never meant to ship.

<AnnotatedCode lang="ts" code={`
const buildPrompt = (customerName: string): string => {
  return \`
    You are an invoicing assistant.
    Customer \${customerName} has unpaid invoices.
    Reply in fewer than 200 words.
  \`;
};
`}>
  <AnnotatedStep meta="{2-6}" color="blue">
    The string keeps every character between the backticks: the leading newline after the opening backtick, the indentation aligning each line with the function body, and the trailing newline before the closing backtick.
  </AnnotatedStep>

  <AnnotatedStep meta="{3-5}" color="orange">
    Each line carries the function-body indentation into the output. That's mildly annoying for a model reading the prompt, and outright broken for whitespace-sensitive formats like YAML or Markdown code fences, where the leading spaces change what the parser sees.
  </AnnotatedStep>
</AnnotatedCode>

The natural reaction is to drag the lines back to the left margin so the content comes out clean. That works, but the source then sits out of step with the surrounding function body, and every editor that reformats code tries to push it back into alignment. The better fix is to keep the source aligned and strip the indentation at runtime, which is a job for a tag, introduced in the next section.

`String.raw` is a built-in tag that returns the template's raw text without processing escape sequences, so `\n` stays two characters. It is handy for Windows paths or regular-expression sources, and seeing `` String.raw`C:\Users\${name}` `` in a library, you'll know what it does.

## A tagged template is a function call

A <Term definition="A function call whose arguments are the static and dynamic pieces of a template literal.">tagged template</Term> looks like new syntax, but underneath it's a function call with the arguments rearranged. `` tag`Hello, ${name}!` `` is the same shape as `tag(['Hello, ', '!'], name)`. The backticks aren't a string going into a function; they're the function-call syntax itself, handing the template's static segments and dynamic values in separately.

The rest is ordinary function-call behavior. Here is a `currency` tag that takes integer-cents numbers, the same `1995` from the "Store cents, not dollars" lesson, and interpolates them as formatted dollar strings.

<AnnotatedCode lang="ts" code={`
const currency = (
  strings: TemplateStringsArray,
  ...values: number[]
): string => {
  return strings.reduce((acc, str, i) => {
    const value = values[i];
    const formatted = value === undefined ? '' : \`$\${(value / 100).toFixed(2)}\`;
    return acc + str + formatted;
  }, '');
};

const cents = 1995;
const message = currency\`Your total is \${cents} including tax.\`;
`}>
  <AnnotatedStep meta={`{1-4} "strings: TemplateStringsArray" "...values: number[]"`} color="blue">
    The tag receives two things: an array of the static string segments (everything between the `${'${}'}` placeholders), and the resolved values from each `${'${}'}`, spread as rest parameters. The `strings` array always has exactly one more element than `values`.
  </AnnotatedStep>

  <AnnotatedStep meta={`{12} "cents"`} color="blue">
    A plain `number`, the same integer-cents value the "Store cents, not dollars" lesson stored. The tag doesn't care where it came from; it just receives a number.
  </AnnotatedStep>

  <AnnotatedStep meta={`{13}`} color="green">
    The tag call. The runtime splits the literal into `['Your total is ', ' including tax.']` and the value `1995`, then passes them to `currency` exactly as if you'd called `currency(['Your total is ', ' including tax.'], 1995)`.
  </AnnotatedStep>

  <AnnotatedStep meta="{5-9}" color="green">
    The tag walks the segments, interleaving each with the formatted value. The result is a regular string, `'Your total is $19.95 including tax.'`.
  </AnnotatedStep>
</AnnotatedCode>

The shape is fixed: a tag always receives a <Term definition="The first argument to a tag function — a readonly array of the static string segments between ${} placeholders.">`TemplateStringsArray`</Term> first and the interpolated values after. What it does with them is up to the tag. It can escape HTML before interleaving, build a parameterized SQL query that never inlines the values into the query text, strip the common leading whitespace from every line, or validate the inputs and throw on bad ones. It can even return something other than a string: a SQL fragment object, a React element, a typed query builder.

You won't write production tags in this course; the two you'll use are imported, not hand-written. This walkthrough is here so you recognize the pattern: when you see `` sql`...` `` or `` dedent`...` `` in later lessons, you'll know what's happening at the call site.

## Two production tags: `` sql`...` `` and `` dedent`...` ``

Two tags belong in a SaaS codebase: one keeps your SQL injection-proof, the other keeps multi-line strings readable. The call-site syntax is identical to the `currency` tag; only the work each one does differs.

### `` sql`...` ``: parameterized queries by default

Every modern SQL client and ORM ships a `sql` tagged template that **automatically parameterizes the interpolated values**. Drizzle exposes one as its escape hatch for the rare queries its query builder can't express. The values inside the `${}` placeholders are sent to the database as separately bound parameters, never as inlined strings.

The shape below is what you'll recognize when a later unit covers Drizzle in full. Ignore the surrounding `db.execute` call for now and focus on the `sql`-tagged literal.

<CodeTooltips tooltips={{
  sql: "Drizzle's tagged template. Returns a SQL fragment with the dynamic values bound as parameters, not interpolated as strings.",
  '${orgId}': 'Sent to the database as a bound parameter ($1), not interpolated into the SQL text. The injection door from the start of the lesson stays shut.',
}}>

```ts
import { sql } from 'drizzle-orm';

const status = 'paid';
const orgId = '019385f0-1234-7000-a000-000000000001';

const rows = await db.execute(
  sql`SELECT id, total_cents FROM invoices
      WHERE org_id = ${orgId} AND status = ${status}
      ORDER BY created_at DESC LIMIT 50`,
);
```

</CodeTooltips>

The tagged-template shape is **what makes the SQL safe by default**, not the developer's discipline. A string built with `+` would inline `orgId` straight into the SQL text, leaving you to escape it by hand every time. The `sql` tag instead binds the value to a numbered placeholder (`$1`, `$2`, and so on) and lets the database driver handle the rest. To write a SQL-injectable Drizzle query, you have to deliberately leave the tagged form, and that escape hatch is named, rare, and a red flag in code review.

:::caution
That escape hatch is `sql.raw`, for the genuine cases where the dynamic part is a column or table name rather than a value. It has no parameterization, by design, so user input never goes through it. The dynamic piece must come from a small fixed allowlist in your code, never from a request.
:::

### `` dedent`...` ``: multi-line strings without indentation noise

The indentation problem from the backticks section is exactly the kind a tag can fix. The <Term definition="An npm package exposing a tagged template that strips the common leading whitespace from every line of a multi-line string.">`dedent`</Term> package exports a tag for it: the source stays aligned with its surroundings, and the runtime output comes out clean.

<CodeVariants>
  <CodeVariant label="Without `dedent`">
    <div data-mark-color="orange">

    ```ts {2-6}
    const buildPrompt = (customerName: string, unpaidCount: number): string => {
      return `
        You are an invoicing assistant.
        Customer ${customerName} has ${unpaidCount} unpaid invoices.
        Reply in fewer than 200 words.
      `;
    };
    ```

    </div>
    **Indentation leaks into the output.** Every line carries the function-body indentation, and the string opens and closes with stray newlines. That's fine if the consumer doesn't care, and broken for YAML, Markdown code fences, or any LLM that reads literal whitespace as part of the prompt.
  </CodeVariant>

  <CodeVariant label="With `dedent`">
    <div data-mark-color="green">

    ```ts {1,4}
    import dedent from 'dedent';

    const buildPrompt = (customerName: string, unpaidCount: number): string => {
      return dedent`
        You are an invoicing assistant.
        Customer ${customerName} has ${unpaidCount} unpaid invoices.
        Reply in fewer than 200 words.
      `;
    };
    ```

    </div>
    **Same source, clean output.** The tag strips the common leading indentation from every line and trims the outer newlines. The source stays aligned with the surrounding function, and the runtime string comes out indentation-free.
  </CodeVariant>
</CodeVariants>

`dedent` earns its place because every alternative has a cost. Un-indenting the string misaligns the source with the surrounding function. Building it with concatenation reintroduces the bug class the lesson opened with. A hand-rolled `.replace(/^ {4}/gm, '')` is just a worse version of what `dedent` already does. One import gives you a consistent shape and a readable source.

You'll meet `dedent` again later in email bodies, system prompts, and test fixtures. The usage is identical every time, so once you recognize it here you'll read it without effort.
