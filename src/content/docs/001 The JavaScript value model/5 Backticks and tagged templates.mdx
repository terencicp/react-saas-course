Two strings, each behind a production bug. The first exposes <Term definition="An attack where text submitted by a user is concatenated into a query and runs as SQL, letting the attacker read or change data the query never intended to touch.">SQL injection</Term>; the second turns a five-line system prompt into a tangle of `+ '\n'` calls. They share one flaw: each is assembled by concatenation. One syntax fixes both, and two tagged templates make the fix safe.

  </CodeVariant>

The fix is the same for both: reach for backticks by default, and add a tag when the string is structured. `` sql`...` `` from Drizzle makes hand-written queries safe; `` dedent`...` `` from npm fixes the indentation.

## Use backticks for interpolation and multi-line strings

A template literal is a string written with backticks instead of single or double quotes, with two additions: `${expression}` interpolation, and newlines preserved as newlines. The expression inside `${...}` can be anything that evaluates to a value.

Four shapes you'll reach for often:

```ts
const path = `/invoices/${invoiceId}`;
const heading = `${count} active invoices`;
const className = `rounded-md ${variant === 'primary' ? 'bg-blue-600' : 'bg-zinc-200'}`;
const log = `User ${user.id} requested invoice ${invoice.id}`;
```

Build any string from variables with a template literal. Reaching for `+` instead loses the placeholder structure that makes the intent obvious, and is the first step toward the two bugs the lesson opened with. Default to single quotes for plain strings, but the moment a `${}` or a newline appears, switch to backticks.

### Multi-line strings and leaked indentation

Backticks preserve newlines, so they are the default for anything spanning more than one line: structured log messages, system prompts, fixture text, email bodies. The catch is that they preserve every character, including indentation the author never meant to ship.

<AnnotatedCode lang="ts" code={`
const buildPrompt = (customerName: string): string => {
  return \`
    You are an invoicing assistant.
    Customer \${customerName} has unpaid invoices.
    Reply in fewer than 200 words.
  \`;
};
`}>
  <AnnotatedStep meta="{2-6}" color="blue">
    The string keeps every character between the backticks: the leading newline after the opening backtick, the indentation aligning each line with the function body, and the trailing newline before the closing backtick.
  </AnnotatedStep>

  <AnnotatedStep meta="{3-5}" color="orange">
    That indentation carries into the runtime output: mildly annoying for a model reading the prompt, and outright broken for whitespace-sensitive formats like YAML or Markdown code fences, where leading spaces change what the parser sees.
  </AnnotatedStep>
</AnnotatedCode>

Dragging the lines back to the left margin cleans the output, but the source then sits out of step with the surrounding function, and formatters keep realigning it. The better fix is to keep the source aligned and strip the indentation at runtime, a job for a tag.

`String.raw` is one built-in tag worth recognizing: it returns the template's raw text without processing escape sequences, so `` String.raw`C:\Users\${name}` `` keeps `\n` as two characters rather than a newline.

## A tag is a function call

A <Term definition="A function call whose arguments are the static and dynamic pieces of a template literal.">tagged template</Term> is a function call with its arguments rearranged. `` tag`Hello, ${name}!` `` has the same shape as `tag(['Hello, ', '!'], name)`: the backticks aren't a string passed to a function, they are the call syntax itself, handing over the static segments and the dynamic values separately.

Here is a `currency` tag that takes integer-cents numbers and interpolates them as formatted dollar strings.

<AnnotatedCode lang="ts" code={`
const currency = (
  strings: TemplateStringsArray,
  ...values: number[]
): string => {
  return strings.reduce((acc, str, i) => {
    const value = values[i];
    const formatted = value === undefined ? '' : \`$\${(value / 100).toFixed(2)}\`;
    return acc + str + formatted;
  }, '');
};

const cents = 1995;
const message = currency\`Your total is \${cents} including tax.\`;
`}>
  <AnnotatedStep meta={`{1-4} "strings: TemplateStringsArray" "...values: number[]"`} color="blue">
    The tag receives two things: an array of the static string segments (everything between the `${'${}'}` placeholders), and the resolved values from each `${'${}'}`, spread as rest parameters. The `strings` array always has one more element than `values`.
  </AnnotatedStep>

  <AnnotatedStep meta={`{12} "cents"`} color="blue">
    A plain `number`, the same integer-cents value the "Storing money as integer cents" lesson stored. The tag just receives a number; where it came from doesn't matter.
  </AnnotatedStep>

  <AnnotatedStep meta={`{13}`} color="green">
    The tag call. The runtime splits the literal into `['Your total is ', ' including tax.']` and the value `1995`, then passes them to `currency(['Your total is ', ' including tax.'], 1995)`.
  </AnnotatedStep>

  <AnnotatedStep meta="{5-9}" color="green">
    The tag walks the segments, interleaving each with its formatted value, and returns a regular string, `'Your total is $19.95 including tax.'`.
  </AnnotatedStep>
</AnnotatedCode>

A tag always receives a <Term definition="The first argument to a tag function — a readonly array of the static string segments between ${} placeholders.">`TemplateStringsArray`</Term> first and the interpolated values after; what it does with them is up to the tag. It can escape HTML, bind values to a parameterized SQL query instead of inlining them, or strip common leading whitespace, and it can return something other than a string: a SQL fragment, a React element, a typed query builder.

You won't write production tag functions in this course; the two you'll use, `` sql`...` `` and `` dedent`...` ``, are imported, and the walkthrough above is so you know what happens at their call sites.

## The two production tags

Two tags are worth knowing on sight: the first keeps your SQL injection-proof, the second keeps multi-line strings readable. Each has the same call-site syntax as the `currency` tag above; only the work differs.

### `` sql`...` ``: parameterized queries by default

Every SQL client and <Term definition="Object-Relational Mapper: a library that maps database tables to objects in your code, letting you query and write rows through typed methods instead of raw SQL strings.">ORM</Term> ships a `sql` tag that **automatically parameterizes the interpolated values**: each value inside a `${}` placeholder reaches the database as a separately bound parameter, never inlined into the query text. Drizzle exposes one as its escape hatch for queries its builder can't express.

Don't worry about the surrounding `db.execute` call yet; focus on the `sql`-tagged literal.

<CodeTooltips tooltips={{
  sql: "Drizzle's tagged template. Returns a SQL fragment with the dynamic values bound as parameters, not interpolated as strings.",
  '${orgId}': 'Sent to the database as a bound parameter ($1), not interpolated into the SQL text. The injection door from the start of the lesson stays shut.',
}}>

```ts
import { sql } from 'drizzle-orm';

const status = 'paid';
const orgId = '019385f0-1234-7000-a000-000000000001';

const rows = await db.execute(
  sql`SELECT id, total_cents FROM invoices
      WHERE org_id = ${orgId} AND status = ${status}
      ORDER BY created_at DESC LIMIT 50`,
);
```

</CodeTooltips>

The tagged-template shape is **what makes the query safe**, not the developer's discipline or a linter rule. A string built with `+` inlines `orgId` straight into the SQL text, leaving escaping to the developer every time; the `sql` tag instead binds each value to a numbered placeholder (`$1`, `$2`, and so on). Writing an injectable query means deliberately leaving the tagged form, a red flag in code review.

  In 6 minutes, Kyle from Web Dev Simplified unpacks a Next.js `sql` template that looked unsafe.
</VideoCallout>

:::caution
When the dynamic part is a column or table name rather than a value, Drizzle offers `sql.raw`, which does no parameterization. Never pass user input through it; its dynamic piece must come from a small fixed allowlist in your code, never from a request.
:::

### `` dedent`...` ``: multi-line strings without indentation noise

A tag also fixes the leaked indentation from the backticks section. The <Term definition="An npm package exposing a tagged template that strips the common leading whitespace from every line of a multi-line string.">`dedent`</Term> package keeps the source aligned with its surroundings while the runtime output comes out clean.

<CodeVariants>
  <CodeVariant label="Without `dedent`">
    <div data-mark-color="orange">

    ```ts {2-6}
    const buildPrompt = (customerName: string, unpaidCount: number): string => {
      return `
        You are an invoicing assistant.
        Customer ${customerName} has ${unpaidCount} unpaid invoices.
        Reply in fewer than 200 words.
      `;
    };
    ```

    </div>
    **Indentation leaks into the output.** Every line carries the function-body indentation, and the string opens and closes with stray newlines. Harmless if the consumer doesn't care, broken for YAML, Markdown code fences, or any LLM that reads literal whitespace as part of the prompt.
  </CodeVariant>

  <CodeVariant label="With `dedent`">
    <div data-mark-color="green">

    ```ts {1,4}
    import dedent from 'dedent';

    const buildPrompt = (customerName: string, unpaidCount: number): string => {
      return dedent`
        You are an invoicing assistant.
        Customer ${customerName} has ${unpaidCount} unpaid invoices.
        Reply in fewer than 200 words.
      `;
    };
    ```

    </div>
    **Same source, clean output.** The tag strips the common leading indentation and trims the outer newlines.
  </CodeVariant>
</CodeVariants>

`dedent` earns its place because every alternative has a cost: un-indenting the string misaligns it from the surrounding code, concatenation reintroduces the bug class the lesson opened with, and a hand-rolled `.replace(/^ {4}/gm, '')` is a brittle reimplementation. One import keeps both the source and the output readable.
