Picture two bugs. A user types 280 emojis into a bio field with a "280-character limit" and gets a "too long" error. Another signs up with a name with an accented letter, and the duplicate check misses an existing row that looks identical on screen. Both trace to the same root: `string.length` in JavaScript counts UTF-16 storage chunks, not the characters a user perceives. This lesson covers which of the three counts to use and how to compare two strings that look identical.

`.length` is a <Term definition={"A property of how a value is stored or transmitted, not of what it represents."}>serialization detail</Term>, not a typo trap for emoji: it tells you how the engine stored the string, not how a human reads it.

## Code units, code points, and grapheme clusters

There's no single "length of a string" in JavaScript. There are three, and each answers a different question, so before reaching for `.length` ask which count you need: code units, code points, or <Term definition={"One character as the user perceives it on screen. Can span multiple Unicode code points — a base letter plus combining marks, an emoji built from a zero-width-joiner sequence, a regional-indicator pair forming a flag."}>grapheme clusters</Term>.

Here is one input measured all three ways:

```ts
const family = '👨‍👩‍👧‍👦';

family.length;                                            // 11
[...family].length;                                       // 7
[...new Intl.Segmenter('en', { granularity: 'grapheme' })
  .segment(family)].length;                               // 1
```

Reach for each in a different situation:

- **Code units**: `string.length`. The right answer when the value is a key, an index back into the same string, or a byte budget for a serialized payload. Fast and correct for ASCII, but wrong for anything the user sees.
- **Code points**: `[...string].length` (or `Array.from(string).length`). A code point is the single number Unicode assigns to one character; the ones above the 16-bit boundary are the surrogate pairs that `.length` double-counts. Spreading a string iterates by code point, so each pair collapses back to one. Closer to what a human would count than `.length`, but still wrong for characters built from joined sequences: the family above is seven code points but one cluster on screen.
- **Grapheme clusters**: `new Intl.Segmenter(locale, { granularity: 'grapheme' })`, then count the segments. The right answer for "how many characters does the user see," so it is what any length check on a user-facing field should use.

## Counting graphemes with `Intl.Segmenter`

`Intl.Segmenter` ships in every browser this course targets and in Node, so you can use it directly.

The one-liner to memorize:

```ts
const countCharacters = (input: string): number =>
  [...new Intl.Segmenter('en', { granularity: 'grapheme' }).segment(input)].length;

countCharacters('🇺🇸');         // 1
countCharacters('👨‍👩‍👧‍👦');     // 1
countCharacters('café');        // 4
```

The constructor takes a **locale** and a **granularity**. The locale matters for scripts where grapheme rules differ (Thai, Khmer, Devanagari); for Latin-script text any locale gives the same boundaries, but one is still required. `'grapheme'` segments by user-perceived character.

`.segment(input)` returns an iterable of `{ segment, index, ... }` objects, one per cluster. It has no `.length` or `.size`, so the idiomatic count spreads it into an array and reads that length.

The same constructor also accepts `'word'` and `'sentence'` granularities; word segments carry an `isWordLike` flag so you can skip punctuation and whitespace.

:::caution
Never truncate a user-facing string at an arbitrary character index. `'👨‍👩‍👧‍👦'.slice(0, 5)` splits the family emoji's code-point sequence into a broken string that renders as "broken character" boxes. When a field needs a hard limit (preview text, an SMS body, a card heading), iterate the segments and concatenate them up to the limit.
:::

## Normalize strings before storing them

Two strings can look identical on screen yet compare as different. The literals below render the same, yet the equality check fails and the length checks disagree:

```ts
const a = 'café';            // precomposed: 'c', 'a', 'f', 'é'
const b = 'café';            // decomposed:  'c', 'a', 'f', 'e' + combining acute
a === b;                     // false
a.length;                    // 4
b.length;                    // 5
```

A user types these as the same word, but they are different sequences of Unicode code points. The first uses a precomposed `é`, one code point that already carries the accent. The second uses a plain `e` followed by a combining acute accent, two code points the renderer overlays into one visual cluster. The previous lesson's rule still holds: for primitives, `===` compares the value, and these values differ.

The fix is one method call:

```ts
a.normalize('NFC') === b.normalize('NFC');   // true
```

`.normalize('NFC')` rewrites both forms to the same canonical sequence. There are four normalization forms:

- **`NFC`** (Canonical Composition): combine characters into their precomposed form. The default for storage, comparison, and search.
- **`NFD`** (Canonical Decomposition): split precomposed characters into a base letter plus combining marks. Useful for accent-insensitive search: decompose, then strip the combining marks.
- **`NFKC`** / **`NFKD`** (Compatibility forms): collapse characters that look similar but are semantically distinct, so the `ﬁ` ligature becomes `fi` and full-width digits become ASCII digits. Useful for fuzzy matching at a search boundary, but wrong for storage because they lose information.

Follow one rule: **normalize once, at the database write boundary**, alongside your input validation. If every value in the table is already NFC, every comparison and length check downstream operates on a canonical form. A `.normalize('NFC')` call inside a comparison helper or search function is the warning sign: walk back to the seam where the value entered the system and normalize it there instead.

## String methods to use, and which to skip

`String.prototype` is large and mostly legacy. A small set earns daily use; the rest you only recognize in older code. The working set:

- **`includes`** / **`startsWith`** / **`endsWith`**: substring tests. Reach for these over `indexOf(needle) !== -1`, which reads as "where is it?" when the question is "is it there?"
- **`at(-1)`**: last-character access, cleaner than `string[string.length - 1]`. Negative indices count from the end.
- **`slice(start, end)`**: substring extraction, and the default choice. Prefer it over `substring` (which silently swaps its arguments if `start > end`) and `substr` (deprecated).
- **`split`** / **`join`**: the boundary between a string and an array of segments: `split(sep)` breaks the string apart, `join(sep)` reassembles it.
- **`replaceAll(needle, replacement)`**: replace every occurrence of a literal string, without the `replace(/needle/g, ...)` regex boilerplate.
- **`trim`** / **`trimStart`** / **`trimEnd`**: whitespace cleanup at input boundaries. Pair with the empty-string guard from the previous lesson when converting form input.
- **`padStart`** / **`padEnd`**: fixed-width formatting for logs and CLI output.
- **`localeCompare(other, locale, options)`**: locale-aware comparison, the right answer for any user-visible alphabetical sort. `<` and `>` compare by code unit, which puts accented characters where no human would call alphabetical.
- **`normalize(form)`**: the boundary tool from the previous section.

The legacy surface, worth recognizing so you can avoid it: `substr` and `substring` (use `slice`), the `escape` / `unescape` globals (use `encodeURIComponent` / `decodeURIComponent`), and the 1990s HTML-wrapping methods like `bold` and `italics` (JSX owns markup here).
