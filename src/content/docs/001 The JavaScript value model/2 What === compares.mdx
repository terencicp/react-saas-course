Two comparisons that surprise most people. The first checks two objects with identical contents.

```ts
console.log({ id: 1 } === { id: 1 }); // false
```

The second checks a value against itself.

```ts
console.log(NaN === NaN); // false
```

JavaScript has three equality operators and two edge cases. Reach for `===` by default, learn the two cases where its answer misleads you, and recognize when another operator fits.

## How `===` compares primitives and objects

`===` asks one question: are these the same value? The answer depends on which kind of value you give it. Primitives are values themselves; objects are references to a value stored elsewhere.

For **primitives**, `===` compares the value. `'ada' === 'ada'` is `true` because the two strings *are* the same value; a primitive has no identity apart from its content. `42 === 42`, `true === true`, and `null === null` are `true` for the same reason.

For **objects**, `===` compares the reference, not the contents it points at. Two object literals with identical contents are separate allocations, so their references differ and `===` returns `false`. The same object reached through two names is `===` to itself: both names hold the same reference.

```ts
console.log('ada' === 'ada');                       // true
console.log({ id: 1 } === { id: 1 });               // false
const user = { id: 1 };
const alias = user;
console.log(user === alias);                        // true
```

`===` never asks whether two values have the same shape; that is a separate question the language has no operator for.

## Why the course never writes `==`

JavaScript's other equality operator, `==`, first runs a table of <Term definition="JavaScript automatically converting a value from one type to another, such as a string to a number, before an operation.">coercion</Term> rules: strings convert to numbers, objects convert to primitives, `null` and `undefined` equal each other but not `false`, with more special cases beyond. The rules are documented but too many to recall mid-task, so `==` is hard to predict. The next chapter covers `??` and explicit nullish checks for the one case where `==` is tempting.

Avoiding `==` takes no discipline: Biome's `noDoubleEquals` rule flags every `==` and `!=` at lint time, turning a slip into a build error rather than something a reviewer must catch.

:::caution
If you see `==` in legacy code or in code from an AI assistant, change it to `===` and re-test. The behavior will change to what you actually wanted.
:::

## `Object.is`: `===` except for `NaN` and `±0`

JavaScript has a third equality form, `Object.is(a, b)`. Despite the name, it has nothing to do with objects; it behaves exactly like `===` except in the two edge cases above, treating `NaN` as equal to itself and `+0` as distinct from `-0`.

```ts
console.log(Object.is(NaN, NaN));     // true   — diverges from ===
console.log(Object.is(+0, -0));       // false  — diverges from ===
console.log(Object.is('ada', 'ada')); // true   — same as ===
console.log(Object.is({}, {}));       // false  — same as ===
```

Two cases call for it: custom <Term definition="Caching a function's result so a repeated call with the same input returns the stored value instead of recomputing it.">memoization</Term> keys that must treat `NaN` as a valid input distinct from "no value"; and React's re-render bailout, where a state setter compares the new value to the old with `Object.is`.

Default to `===`, and reach for `Object.is` only in those two cases. When you do, add a comment explaining why, or the next reader will assume it's a typo for `===`.

## `Number.isNaN` over the global `isNaN`

Because `NaN === NaN` is `false`, `if (x === NaN)` can never catch a `NaN`. You need a dedicated function; JavaScript provides two, but only one is safe.

The global `isNaN(x)` coerces its argument to a number before testing. So `isNaN('hello')` is `true` not because `'hello'` is `NaN`, but because coercing it to a number *produces* `NaN`.

`Number.isNaN(x)` skips the coercion, returning `true` only when the value you pass is the actual `NaN`.

## JavaScript has no structural-equality operator

One comparison remains: checking whether two objects hold the same fields and values. JavaScript has no operator or function for it. Comparing `{ id: 1, name: 'Ada' }` to a matching object takes either a third-party library (`fast-deep-equal`, `lodash.isEqual`) or a hand-written recursive walk, and this course uses neither early on.

Instead it teaches patterns that avoid the question. <Term definition="Comparing two objects by whether their fields and values match, recursively. JavaScript has no built-in operator for this; the course's patterns sidestep the need.">Structural equality</Term> rarely needs writing by hand when the data model is shaped well:

- **Compare by primary key.** Two invoice rows are the same invoice when `a.id === b.id`, and only then. Database-shaped data carries its identity in the ID column, so equality at the application layer reduces to comparing two strings.
- **Derive a stable string key from the relevant fields.** To detect changes for caching or deduplication, build a key (`` `${invoiceId}:${status}:${updatedAt}` ``) and compare strings.
- **Use discriminated unions where each variant has its own shape.** A later chapter covers these; comparison then turns on the discriminant field, not the whole object.
